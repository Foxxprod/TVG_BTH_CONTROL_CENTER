BIATH CONTROL CENTER - CONTEXTE DU PROJET
============================================

Ce fichier a ete entierement reecrit le 25/08/2026 pour refleter l'etat reel
du projet apres une premiere phase de developpement. Il remplace la version
initiale (qui decrivait un projet vide, au stade de conception).


1. OBJECTIF DU PROJET
----------------------

Biath Control Center est un logiciel de controle pour piloter les habillages
televisuels pendant une course de biathlon.

Le logiciel permet a un operateur de suivre les donnees de la course en
temps reel et de declencher les habillages graphiques dans CasparCG de
maniere rapide, fiable et comprehensible pendant une diffusion en direct.

Un logiciel distinct (deja existant, non modifie par ce projet) genere et
diffuse les donnees de la course de biathlon via WebSocket. Biath Control
Center consomme ces donnees et pilote CasparCG ; il ne remplace pas le
logiciel de donnees.


2. ETAT ACTUEL DU REPO
----------------------

Fichiers principaux :

- main.py
    Point d'entree. Charge config.json (app_config.load_config), cree les
    instances globales `caspar` (CasparCG) et `data` (BiathDataWebsocket)
    a partir de ce config, declare la page NiceGUI ("/"), appelle
    build_header(caspar, data, config), build_body() et build_footer(),
    connecte caspar/data au demarrage du serveur (@app.on_startup), lance
    ui.run().

- app_config.py
    load_config()/save_config(config) : lit/ecrit config.json (theme
    clair/sombre, titre du logiciel, ip/port du serveur de donnees,
    ip/port CasparCG, numeros de channel preview/programme). Fichier
    absent ou incomplet -> complete avec DEFAULT_CONFIG. config.json N'EST
    PAS commite (voir .gitignore) : c'est un reglage d'instance/machine,
    contrairement a templates.json (catalogue de graphiques, commite). Le
    dict `config` charge dans main.py est passe par reference a
    build_header, qui le modifie et le sauvegarde depuis la boite de
    dialogue Parametres (voir 6.1) - source de verite unique partagee.

- casparcg.py
    Couche de communication AMCP avec CasparCG. Implementation maison
    (pas de librairie tierce) : ouverture de socket TCP brut, envoi de
    commandes texte, parsing des reponses selon le protocole AMCP.
    Contient la classe CasparCG et le dataclass AMCPResponse.

- biathdata_ws.py
    Couche de communication WebSocket avec le logiciel de donnees
    biathlon. Utilise la librairie tierce `websockets` (contrairement a
    casparcg.py, le protocole WebSocket est trop complexe/risque a
    reimplementer a la main). Contient la classe BiathDataWebsocket.

- interface.py
    Construction de l'interface NiceGUI : barre d'outils du haut
    (build_header) et corps de page (build_body). Ne contient aucune
    logique bas niveau AMCP/WebSocket, uniquement de l'affichage et des
    appels aux methodes publiques de CasparCG/BiathDataWebsocket.
    build_body divise le corps en 3 conteneurs empiles verticalement
    (PRE RACE / RACE / POST RACE, voir SECTIONS), chacun organise en une
    VRAIE grille CSS (fonction interne add_button(section, row, column,
    **kwargs_scene_button)) : chaque case est un ui.column positionne
    explicitement via grid-row/grid-column (style CSS), pas des ui.row
    flex independantes par ligne - sinon "colonne N" ne s'alignerait pas
    entre les lignes (bug reel rencontre et corrige : avec des lignes flex
    independantes, la colonne N d'une ligne n'est que sa N-ieme case a
    elle, sans lien avec la colonne N d'une autre ligne qui a moins
    d'entrees). Les 3 conteneurs ne se partagent PAS la hauteur a parts
    egales : PRE RACE et POST RACE se reduisent a leur hauteur de contenu
    (comportement flex par defaut, flex-grow 0), RACE absorbe tout le
    reste de la hauteur disponible (flex-1) - ex: POST RACE avec 2
    boutons reste compact, RACE s'etend d'autant plus. Choix explicite de
    l'utilisateur, RACE cible en dur (pas de logique dynamique "la section
    avec le plus de contenu grandit" - non faisable en CSS pur sans mesurer
    le contenu en JS). Les boutons a creer sont lus depuis templates.json
    via buttons_config.load_button_configs().

- buttons_config.py
    load_raw_configs() : lit templates.json TEL QUEL (liste brute, sans
    filtrage). load_button_configs(raw=None)/load_column_titles(raw=None) :
    filtrent+valident (boutons vs titres de colonne "_column_title", en
    ignorant "_example") ; si `raw` est fourni (voir build_body), evite une
    relecture independante du fichier - important pour que les dicts
    obtenus soient les MEMES objets que ceux geres ailleurs (persistance,
    voir plus bas). save_button_configs(raw) : reecrit integralement le
    fichier. Renvoie [] avec un message si le fichier est absent. Leve une
    ValueError si le JSON n'est pas une liste ou si un champ obligatoire
    manque sur une definition (section/label/template/layer pour un
    bouton, section/column/title pour un titre de colonne).

- templates.json
    Catalogue des boutons de l'interface, un objet JSON par SceneButton.

3. TECHNOLOGIES CONFIRMEES
---------------------------

- Python (3.13 en dev).
- NiceGUI pour l'interface operateur (confirme et utilise).
- asyncio pour tout le code reseau et les taches de fond (reconnexion,
  ping, retrait automatique de graphiques...).
- Client AMCP : implementation interne maison sur socket TCP brut (pas de
  librairie tierce). Choix assume : protocole texte simple, controle total
  du comportement (timeouts, reconnexion), pas de dependance externe a
  maintenir pour un usage broadcast en direct.
- Client WebSocket : librairie tierce `websockets` (pip install websockets).
  Choix assume different d'AMCP : le protocole WebSocket (handshake HTTP
  Upgrade, framing, masking, ping/pong de controle) est trop complexe et
  risque a reimplementer correctement a la main.
- Aucune API web publique construite par-dessus NiceGUI : NiceGUI gere la
  communication navigateur <-> serveur en interne.


4. CASPARCG.PY - DETAIL DE L'IMPLEMENTATION
---------------------------------------------

4.1 AMCPResponse (dataclass)
    - code: int, message: str, data: list[str]
    - is_info      -> 100 <= code < 200
    - is_success    -> 200 <= code < 400
    - is_error      -> code == 0 (erreur locale/reseau) ou code >= 400

4.2 Classe CasparCG - constructeur
    CasparCG(ip, port, channel_programm, channel_preview, timeout=5.0,
             reconnect=True, reconnect_delay=5.0)
    channel_programm/channel_preview DOIVENT correspondre aux channels
    reellement definis dans le casparcg.config du serveur CasparCG cible
    (voir section 7, un mismatch a deja cause une erreur "Invalid channel
    specified").

    Etat interne : reader/writer asyncio, connected (bool), _lock
    (asyncio.Lock, serialise les commandes), _preview (dict, dernier
    template/data/cg_layer/play_on_load envoye en preview), _ping_interval
    (5.0s), _ping_task, _remove_delay (5.0s), _pending_removals (dict
    (address, cg_layer) -> Task, pour l'auto-remove differe apres stop()),
    last_ping_ms (float | None - temps d'aller-retour du dernier PING/PONG
    reussi, mesure directement dans ping() autour de l'ecriture/lecture
    existantes ; None tant qu'aucun ping n'a reussi. Affiche au survol du
    statut CASPAR CG du header, voir 6.1 - demande explicite de
    l'utilisateur).

4.3 Fonctions internes/techniques (prefixees _, ou non destinees a un
    usage direct depuis le reste du logiciel) :
    - ping() : envoie "PING\r\n", compare la reponse brute a "PONG" (PING
      est un cas special du protocole AMCP, il ne suit PAS le format
      "XXX message" standard), met a jour self.connected.
    - _ping_loop() : boucle unique de fond. Si connecte -> attend
      ping_interval puis ping(). Si deconnecte et self.reconnect ->
      attend reconnect_delay puis _reconnect(). Sinon, arrete la boucle.
      Sequentiel : jamais deux tentatives de reconnexion en parallele.
    - _reconnect() : ferme l'ancienne connexion si presente, en ouvre une
      nouvelle, appelle ping().
    - send_command(command) : envoie une commande AMCP brute, retourne un
      AMCPResponse. Retourne code=0 "Not connected" si non connecte.
    - _read_response() : parse une reponse (code + message), et pour les
      reponses multi-lignes (code 200), continue de lire jusqu'a une
      ligne vide terminale.
    - _channel_number(channel) : "prw" -> channel_preview, "pgm" ->
      channel_programm, sinon ValueError.
    - format_address(channel, layer=None) : "prw" -> toujours
      "{channel_preview}-1" (layer ignore, force a 1). "pgm" -> exige un
      layer explicite (ValueError sinon).
    - _escape_amcp_string(value) / _escape_xml(value) : echappement pour
      parametres AMCP entre guillemets et pour attributs XML.
    - format_template_data(data: dict) : convertit un dict cle/valeur en
      XML CasparCG classique :
        <templateData><componentData id="CLE"><data id="text"
        value="VALEUR"/></componentData>...</templateData>
      CONFIRME avec un exemple XML reel fourni par l'utilisateur. Les
      cles du dict correspondent aux VRAIS noms de champs du template
      (pas de convention generique f0/f1) : chaque template a ses propres
      noms de champs.
    - _schedule_remove(...) / _delayed_remove(...) : programment un
      CG REMOVE automatique remove_delay secondes apres un stop(), annule
      si un nouveau graphique est charge sur le meme (channel-layer,
      cg_layer) avant l'echeance.

4.4 Fonctions publiques (a utiliser depuis le reste du logiciel) :
    - connect() : ouvre la connexion TCP, verifie via PING/PONG, DEMARRE
      TOUJOURS la boucle de fond _ping_loop meme si cette premiere
      tentative echoue (pour que CasparCG indisponible au demarrage soit
      retente automatiquement au lieu d'abandonner). Retourne None ou un
      message d'erreur.
    - disconnect() : envoie BYE (sur, car on est toujours en connexion
      distante/reseau, jamais en console locale CasparCG - BYE ne fait
      donc que deconnecter, il n'eteint pas le serveur) puis ferme le
      socket. Annule _ping_task et toutes les taches _pending_removals.
    - play_template(channel, template, data=None, layer=None, cg_layer=1,
      play_on_load=True) : construit et envoie CG ADD. Si succes, annule
      tout auto-remove programme pour ce (channel-layer, cg_layer), et si
      channel=="prw", memorise l'etat dans self._preview.
    - update_template(channel, data, layer=None, cg_layer=1) : CG UPDATE.
      Met a jour self._preview["data"] si c'est la preview qui est mise a
      jour avec succes.
    - remove_template(channel, layer=None, cg_layer=1) : CG REMOVE
      (retire completement le producer, contrairement a stop()).
    - invoke_template(channel, function, layer=None, cg_layer=1) : CG
      INVOKE - appelle une fonction/methode DEJA EXPOSEE par le template
      charge sur ce channel/layer/cg_layer (ex: une animation JS nommee
      d'un template HTML), sans toucher au producer lui-meme (pas d'ADD/
      REMOVE/UPDATE). Demande explicite de l'utilisateur, verifiee auprès
      de la doc AMCP officielle avant implementation (l'utilisateur a
      specifiquement demande de verifier plutot que de faire confiance a
      la memoire du modele - bon reflexe, une premiere version avait
      entoure `function` de guillemets par analogie avec CG ADD/UPDATE) :
      la syntaxe reelle est "CG [channel]-[layer] INVOKE [cg_layer]
      [method]" avec `method` en token NU, SANS guillemets (exemple
      officiel : "CG 1-1 INVOKE 1 start_intro", source server/docs/
      source/amcp/template-graphics-commands.rst du repo CasparCG) -
      `function` ne doit donc jamais contenir d'espace. Utilise par
      SceneButton.invoke_all_pgm() (voir section 7) pour le bouton
      SPONSOR IN du footer (voir 6.3).

      BUG REEL RENCONTRE ET CORRIGE juste apres la mise en prod de
      SPONSOR IN : "je ne suis plus connecte a casparCG une fois que
      j'appuye sur le bouton". Root-cause CONFIRMEE en lisant le CODE
      SOURCE OFFICIEL de CasparCG (github.com/CasparCG/server, src/
      protocol/amcp/AMCPCommandsImpl.cpp) : CG INVOKE renvoie le code
      201 ("execute, PLUS UNE LIGNE de donnee" - le resultat de l'appel
      JS), PAS 202 comme CG ADD/PLAY/STOP/REMOVE/CLEAR/UPDATE (deja
      utilises partout ailleurs dans ce fichier, "execute, aucune donnee
      supplementaire" - c'est pourquoi ce bug etait reste invisible
      jusqu'ici, invoke_template etant la toute PREMIERE commande 201
      jamais envoyee par ce logiciel). _read_response() ne savait lire
      des lignes supplementaires QUE pour le code 200 (bloc termine par
      une ligne vide) - la ligne de donnee du code 201 restait donc NON
      LUE dans le tampon TCP, decalant la lecture de TOUTES les reponses
      suivantes d'une ligne. Consequence observee : le PING PERIODIQUE
      suivant (_ping_loop, toutes les 5s) lisait cette ligne perimee au
      lieu de "PONG", ping() renvoyait donc False, et self.connected
      passait a False - exactement le symptome signale, quelques
      secondes apres l'appui sur SPONSOR IN.
      CORRIGE dans _read_response() : le code 201 lit maintenant
      EXACTEMENT UNE ligne de donnee supplementaire (pas de boucle
      jusqu'a une ligne vide, contrairement au 200). Verifie avec un
      faux serveur TCP reproduisant EXACTEMENT le format reel de
      CasparCG ("201 CG OK\r\n" + resultat + "\r\n") : invoke_template
      lit bien les 2 lignes, la commande suivante n'est plus decalee, et
      un ping() juste apres continue de repondre correctement (y compris
      apres 2 CG INVOKE consecutifs, pour ecarter tout decalage
      cumulatif).
    - stop(channel, layer=None, cg_layer=1) : CG STOP, puis programme un
      CG REMOVE automatique 5s plus tard (annulable, voir 4.3).
    - clear(channel, layer=None) : CLEAR generique (retire N'IMPORTE quel
      producer, video/image/graphique, pas seulement les templates CG).
      Si layer est omis, clear tout le channel. Reinitialise self._preview
      si c'est la preview qui est cleared avec succes.
    - play_prw_to_pgm(layer) : le "Take". Rejoue (recopie la commande et
      les donnees, choix assume plutot que cloner une composition deja
      preparee) le template/data actuellement memorise en preview vers le
      programme au layer donne, puis stoppe la preview. Retourne une
      erreur "Nothing in preview to take" si rien n'a ete joue en preview
      au prealable (ou si le dernier play a echoue).
    - emergency_all_out() : clear("prw") + clear("pgm"), retourne les deux
      AMCPResponse. Vide integralement les deux channels (tout producer,
      y compris les graphiques).
    - change_connection(ip=None, port=None, channel_preview=None,
      channel_programm=None) : disconnect() puis met a jour les attributs
      fournis (les autres restent inchanges) puis connect(). Retourne None
      ou un message d'erreur (meme contrat que connect()). Utilise par la
      boite de dialogue Parametres (voir 6.1) pour appliquer un changement
      d'IP/port/channel EN DIRECT, sans redemarrer le logiciel. Reconnecte
      toujours (meme un simple changement de channel, qui ne necessite pas
      forcement une nouvelle connexion TCP) - choix assume par simplicite.

4.5 Rappels de protocole AMCP (source : wiki AMCP CasparCG, la doc note
    elle-meme qu'elle peut etre datee, a re-verifier avec
    casparcg.com/docs/wiki si besoin) :
    - Reponses : code 3 chiffres + message. 100-101 info. 200-202 succes
      (200 = multi-lignes terminees par une ligne vide, 201/202 = une
      seule ligne). 400-404 erreur client. 500-503 erreur serveur.
    - Encodage UTF-8, terminaison de commande "\r\n".
    - Parametres avec espaces entre guillemets, echappement \" et \\.
    - Adressage channel-layer : "1" (tout le channel), "1-1", "1-10",
      "-0" (layer par defaut).
    - CG ADD [layer] "template" [play-on-load 0/1] {"data"}
    - CG UPDATE [cg_layer] "data"
    - CG REMOVE [cg_layer]
    - CG STOP [cg_layer]
    - CG CLEAR (sans cg_layer, ne retire que les templates CG)
    - CLEAR (generique, retire tout producer)
    - BYE deconnecte a distance / eteint le serveur en local.


5. BIATHDATA_WS.PY - DETAIL DE L'IMPLEMENTATION
--------------------------------------------------

5.1 Classe BiathDataWebsocket - constructeur
    BiathDataWebsocket(ip, port, path="/", timeout=5.0, reconnect=True,
                        reconnect_delay=5.0)
    url (property) = f"ws://{ip}:{port}{path}"

    Etat expose : latest_data (dict JSON brut du dernier message de
    chronometrage complet), config (SimpleNamespace), event_infos
    (SimpleNamespace), timing_data (dict[str, SimpleNamespace] cle =
    dossard), connected (bool), last_ping_ms (float | None - temps
    d'aller-retour du dernier ping/pong WebSocket NATIF reussi (frame de
    controle, pas un message de donnees), mesure par _ping_loop toutes
    les _ping_interval=5.0s ; None tant qu'aucun ping n'a reussi. Affiche
    au survol du statut WS DATA du header, voir 6.1 - demande explicite
    de l'utilisateur : "si c'est pas trop complique, le ping". _ping_loop
    tourne en TACHE SEPAREE de _receive_loop (occupee a iterer les
    messages entrants) - la bibliotheque `websockets` gere ping/pong
    independamment des frames de donnees sur la meme connexion, verifie
    reellement (serveur de test local, receive_loop et ping_loop actifs
    en meme temps sans interference) plutot que suppose).

5.2 Fonctions publiques :
    - connect() : ouvre la connexion websocket, DEMARRE TOUJOURS la
      boucle de fond _receive_loop meme si la premiere tentative echoue
      (meme logique que CasparCG.connect(), pour retenter automatiquement
      un serveur de donnees indisponible au demarrage) - demarre aussi
      _ping_loop (voir plus haut).
    - disconnect() : annule _receive_task, ferme la connexion.
    - change_ip(ip, port=None) : met a jour l'adresse ; si deja connecte,
      se deconnecte puis se reconnecte a la nouvelle adresse.
    - on_message(callback) : abonne callback (fonction synchrone, sans
      argument) - appele des qu'un nouveau message complet est traite
      avec succes (voir _handle_message). Voir scene_button.py section
      "Rafraichissement instantane sur nouvelle donnee".
    - remove_listener(callback) : desabonne callback (sans erreur si deja
      absent) - a appeler quand l'abonne n'a plus besoin d'etre notifie
      (ex: page/client ferme), self etant un singleton partage entre
      tous les clients.

5.3 Fonctions internes :
    - _receive_loop() : boucle unique de fond, meme principe que
      _ping_loop de CasparCG. Si connecte, consomme les messages
      (async for) jusqu'a perte de connexion. Si deconnecte et
      self.reconnect, attend reconnect_delay puis _reconnect(). Jamais
      deux tentatives en parallele.
    - _reconnect() : ferme l'ancien websocket si present, en ouvre un
      nouveau.
    - _handle_message(raw_message) :
        1. json.loads(raw_message). PARTICULARITE DECOUVERTE EN TEST : le
           serveur encode parfois le JSON DEUX FOIS (le message recu est
           une string JSON qui contient elle-meme du JSON en texte
           echappe). Le code detecte ce cas (resultat = str) et refait un
           second json.loads.
        2. Si le dict resultant contient les cles "config", "event_infos"
           ET "timing_data", c'est un snapshot COMPLET de chronometrage
           (pas un delta) : latest_data, config, event_infos et
           timing_data sont remplaces integralement, PUIS chaque
           callback abonne via on_message() est appele (try/except
           individuel - voir 5.2 et section "Rafraichissement instantane
           sur nouvelle donnee" de scene_button.py).
        3. D'AUTRES TYPES DE MESSAGES passent sur le meme WebSocket
           (confirme par l'utilisateur) mais ne sont PAS encore geres :
           ils sont ignores silencieusement pour l'instant. A implementer
           plus tard.
    - _sanitize_key(key) : remplace tout caractere non valide pour un
      attribut Python (ex: espace) par "_". Necessaire car le JSON reel
      contient au moins une cle avec espace : "EVENT NAME" ->
      accessible via event_infos.EVENT_NAME.
    - _to_namespace(data: dict) : convertit un dict en SimpleNamespace en
      assainissant les cles.

5.4 Format reel des messages WebSocket : voir biathdata_reference.txt
    pour le detail complet champ par champ. Points cles :
    - Chaque message de chronometrage contient un etat COMPLET (pas un
      delta), a remplacer integralement a chaque reception.
    - timing_data est indexe par dossard (string), ex: "1", "2"...
    - Les noms de champs (C_NUM, C_LAST_NAME, C_TIME, C_STATUS,
      C_INTERSHOOT1..8, C_INTERSLOPE1..12, etc.) sont documentes dans
      biathdata_reference.txt avec leur variable d'acces exacte.
    - C_START et les C_INTER... sont TRES PROBABLEMENT en millisecondes
      depuis minuit (deduit, pas confirme par le fournisseur).
    - VOLADBNUMBER et C_SHOOTING_RACE_NUMBER : signification non
      identifiee avec certitude.


6. INTERFACE.PY - DETAIL DE L'IMPLEMENTATION
-----------------------------------------------

6.1 build_header(caspar, data, config)
    Barre d'outils fixe en haut de page (ui.header), style sombre
    (bg-slate-900), avec marge (m-3) et coins arrondis sur les 4 cotes
    (rounded-2xl, overflow-hidden pour que les elements colles respectent

6.2 build_body(caspar, data, config)
    Corps de page. Voir section 2 (description du fichier interface.py)
    pour le detail a jour : 3 conteneurs empiles (PRE RACE/RACE/POST
    RACE), grille CSS ligne/colonne par conteneur, boutons lus depuis
    templates.json. `config` (ajoute avec la fonctionnalite de restriction
    par sexe/categorie, voir 7) permet a add_restrict_controls (plus bas)
    de lire/persister l'etat des 2 cases a cocher globales.

    _get_or_create_cell(section, row, column) factorise la logique
    (jusque-la dupliquee dans add_button) de recuperation/creation d'une
    case de la grille CSS - reutilisee par add_button ET
    add_restrict_controls (voir plus bas), plusieurs elements sur la
    meme case s'empilent verticalement. Coercion defensive int(row)/
    int(column) (voir PIEGE ci-dessous, distinct de celui sur `config`) -
    templates.json etant edite a la main, ces valeurs finissent facilement
    en string (ex: "1" au lieu de 1), ce qui plantait `row + 1`
    (TypeError, bug reel rencontre sur une entree _restrict_controls
    reelle de l'utilisateur). add_column_title fait la meme coercion sur
    `column` (n'utilise pas _get_or_create_cell, chemin de code separe).

    add_restrict_controls(section, column) - PAS de parametre "row" :
    place, dans la colonne choisie par templates.json (entree
    "_restrict_controls": true, voir buttons_config.py), les 2 cases a
    cocher globales "restreindre par sexe"/"par categorie" - un peu comme
    un titre de colonne ou un bouton, PAS fixe dans le header (exigence
    explicite de l'utilisateur : "on peut choisir ou placer le
    conteneur"). row FORCE a 1 en interne (_get_or_create_cell(section, 1,
    column)), un "row" present dans l'entree JSON est ignore silencieusement
    - CORRECTION suite a une demande explicite de l'utilisateur : "fait en
    sorte que les case a cocher de restrict soit forcement en haut dans la
    pile d'element de la colonne, juste en dessous du titre". Pour que ce
    soit vrai MEME quand un bouton partage la meme case (row=1) que ces
    cases a cocher (l'empilement dans une case suit l'ordre d'INSERTION,
    pas le contenu), _restrict_controls est traite EN PREMIER dans
    build_body, avant la boucle des boutons (voir plus bas) - garantit que
    ces cases sont toujours le tout premier enfant de leur case. Chaque
    case, au changement, persiste dans config.json (save_config) ET
    appelle immediatement SceneButton.set_restrict_by_sex/
    set_restrict_by_cat (voir 7) pour repercuter le changement sur tous
    les boutons concernes deja a l'ecran.

          jamais planter sur un format de course inhabituel).
        - compute_race_progress(config, timing_data) -> RaceProgress|None :
          calcule TOUT (voir AthleteProgress/RaceProgress) :
            - temps ecoule = DIFFERENCE avec le PROPRE C_START de chaque
              athlete (pas le temps brut cumule depuis minuit) - necessaire
              pour rester correct en depart decale (ex: INDIVIDUAL), sinon
              comparer des temps bruts entre athletes a depart different
              n'aurait aucun sens.
            - athletes exclus : C_STATUS "DNS"/"DNF", ou C_START invalide
              (pas encore parti).
            - position actuelle d'un athlete = le checkpoint le PLUS AVANCE
              de la sequence pour lequel il a une valeur > 0 ("0 = non
              atteint", voir biathdata_reference.txt).
            - LEADER : le plus avance, le plus rapide en cas d'egalite.
            - 1ER <CATEGORIE>/1ER H/1ER D : meme calcul, restreint au
              groupe (5 CATEGORIES fixes + 2 sexes).
            - NOUVEAU LEADER ? (exigence LITTERALE de l'utilisateur :
              "celui qui pour son dernier intermediaire connu est sorti
              avec la position de premier") : parmi tous SAUF le leader
              general, celui classe 1er au classement de SON PROPRE
              checkpoint actuel - c-a-d le plus rapide parmi TOUS ceux
              ayant atteint ce meme point, y compris des athletes qui l'ont
              depasse depuis. Signale un athlete plus rapide que quiconque
              ne l'a ete a ce point, meme s'il n'a pas encore rejoint le
              leader. Le plus avance des candidats est retenu en cas
              d'egalite (menace la plus immediate).
            - 2E/3E (podium general) : calcules dans tous les cas, mais
              n'apparaissent QUE dans la vue etendue de l'UI (voir plus
              bas) - un marqueur purement 2E/3E (sans LEADER/1ER*/NOUVEAU)
              est filtre en vue compacte.
          Renvoie None tant qu'il n'y a rien a afficher (pas de config.
          interorder, ou aucun athlete eligible) - l'appelant doit alors
          ne rien afficher plutot qu'une ligne vide.
        - format_elapsed(ms) : mm:ss (ou h:mm:ss au-dela d'une heure),
          affichage uniquement (tooltips).
        - Teste par ~25 assertions unitaires (donnees synthetiques
          couvrant : leader general, leaders categorie/sexe, potentiel
          nouveau leader avec depart decale, exclusion DNS/DNF/pas-parti,
          podium, cas limites config/timing_data absents) - toutes OK.

    interface.py (_build_race_progress_section, dans build_footer) :

7. SCENE_BUTTON.PY - DETAIL DE L'IMPLEMENTATION
----------------------------------------------------

Classe SceneButton : represente un graphique CasparCG pilotable. Concu
comme LE moyen d'ajouter facilement un nouveau graphique a l'interface et
de controler les donnees qui lui sont envoyees.

Constructeur :
    SceneButton(caspar, data, label, template, layer, cg_layer=1,
                extra_data=None,
                send_ip=False, field_ip="ip",
                bib_on=False, field_bib="bib",
                multipage_on=False, field_page="page",
                reset_page_on_play=False,
                target_on=False, field_target="target",
                free_texts=None)

    Les noms de champs (field_ip, field_bib, field_page, field_target)
    sont CONFIGURABLES par bouton (chaque template CasparCG peut avoir
    ses propres noms de champs), SAUF que la VALEUR du champ ip est
    toujours automatiquement celle du serveur websocket (data.ip), non
    saisie par l'operateur. send_ip n'envoie que l'IP, pas le port.

Comportement au clic (corps du bouton, forme pilule rounded-full comme
le bouton EMERGENCY) :
    - etat "idle"      -> clic = play_template vers preview
    - etat "preview"   -> clic = play_prw_to_pgm (Take vers programme)
    - etat "programme" -> clic sans effet (protection contre un replay
      accidentel d'un graphique en direct ; seul le survol "OUT" peut
      l'arreter)

Survol : un petit rectangle apparait directement au-dessus du bouton
(colle, sans espace mort, pour rester cliquable en y deplacant la
souris), fond noir/gris fonce (bg-slate-800) :
    - "IN"  (idle/preview) -> clic = envoi DIRECT au programme (sans
      passer par la preview)
    - "OUT" (programme)    -> clic = stop() du graphique

Multipage (multipage_on=True) : fleches gauche/droite integrees dans le
corps du bouton (chevron_left/chevron_right). Le compteur "page"
s'incremente/decremente SANS limite haute (plancher a 1, decision
utilisateur : "compteur infini"). Si le graphique est deja affiche, le
changement de page pousse immediatement un update_template.

Selection de dossard (bib_on=True) : boite de dialogue (_ask_bib) avec un
champ de recherche texte (autofocus fiabilise par .props("autofocus") + un
ui.timer de secours qui force le focus), qui filtre en direct la liste
des athletes (data.timing_data, tri par dossard croissant, recherche sur
"dossard - NOM prenom") dans une variable locale `filtered` recalculee a
chaque frappe. Navigation : fleches haut/bas (keydown.up/down.prevent)
deplacent un index de surlignage `selected_index[0]` dans `filtered`
(liste circulaire, retour au debut/fin), Entree ou le bouton "Valider"
confirment l'athlete actuellement surligne (`confirm_selected`). Chaque
ligne de la liste reste aussi cliquable individuellement (selection
directe, liste scrollable). Si le champ de recherche est vide,
`selected_index[0]` demarre a -1 : RIEN n'est surligne par defaut (il
faut taper, cliquer, ou utiliser les fleches pour commencer a naviguer
dans la liste complete).

Le dossard est capture une seule fois au premier play, puis reutilise tel
quel pour le Take (comme les autres donnees memorisees dans
CasparCG._preview). Une fois selectionne, l'athlete choisi est affiche
SOUS le bouton (dans la meme box bordee que les eventuels free_texts, voir
SceneButton._build : la box n'apparait que si bib_on ou free_texts est
actif) avec une icone crayon a cote (_build_bib_display) qui rouvre
_ask_bib a tout moment, pas seulement au premier play
(_on_change_bib_click) : si le graphique est deja affiche (preview ou
programme), le nouveau dossard est pousse immediatement via
update_template, sinon juste memorise pour le prochain play.

Saisie de target (target_on=True) : apres le PREMIER play reussi
(preview ou direct-pgm via "IN" ; pas re-demande au moment du Take),
boite de dialogue avec un champ numerique borne entre 1 et 30. La valeur
saisie est envoyee via update_template.

Champs de saisie libre (free_texts=[{...}, ...]) : zone(s) de saisie
affichees SOUS le bouton (pas dans une boite de dialogue, contrairement a
bib_on/target_on), une par entree de la liste. Chaque entree : "field"
(cle envoyee au template, obligatoire), "label" (affiche sur le champ,
defaut = field), "options" (liste de strings, optionnelle).
    - Sans "options" : une seule ligne, simple ui.input texte libre.
    - Avec "options" : DEUX lignes - une combo box (ui.select, limite aux
      options) ET un ui.input texte libre juste en dessous (label "Texte
      libre"), mutuellement exclusifs : choisir une valeur dans la combo
      box vide le texte libre (input_widget.set_value(None)) et
      inversement taper dans le texte libre deselectionne la combo box,
      via on_value_change() de chaque widget. _build_payload() prend la
      valeur du select si non vide, sinon celle de l'input. Une icone "+"
      (add_circle) a cote de la combo box ouvre une petite boite de
      dialogue (_on_add_free_text_option) pour AJOUTER UNE NOUVELLE
      OPTION EN DIRECT : ajoutee a select_widget.options (utilisable/
      selectionnee immediatement, sans redemarrer) ET a free_text
      ["options"] (le MEME dict que celui charge depuis templates.json,
      voir interface.build_body - donc persistee dans le fichier via
      self._on_config_changed(), fourni par add_button). scene_button.py
      ne sait pas ou/comment ecrire templates.json (separation des
      responsabilites, section 11) : on_config_changed est une simple
      callback fournie par interface.py (persist_templates(), qui
      reecrit raw_configs entier via buttons_config.save_button_configs).
      IMPORTANT : build_body charge templates.json UNE SEULE FOIS via
      load_raw_configs() (pas un load_button_configs()/load_column_titles
      () independants comme avant) precisement pour que les dicts
      free_text passes aux SceneButton soient les MEMES objets que ceux
      contenus dans raw_configs - une mutation de l'un mute l'autre,
      necessaire pour que la persistance reflete bien l'ajout.
      Une icone "-" (remove_circle, demande explicite ulterieure : pouvoir
      supprimer une option deja enregistree) juste a cote du "+" supprime
      l'option ACTUELLEMENT SELECTIONNEE dans la combo box (pas un
      dialogue de gestion listant toutes les options - reutilise la
      selection deja faite par l'operateur) : _on_remove_free_text_option
      notifie ("Selectionnez d'abord...") si rien n'est selectionne, sinon
      demande confirmation (petite boite de dialogue Annuler/Supprimer,
      contrairement a l'ajout qui n'a pas besoin de confirmation - une
      suppression fait perdre l'option pour de bon) avant de retirer la
      valeur de free_text["options"] et de rafraichir select_widget.
      options, puis appelle self._on_config_changed() exactement comme
      l'ajout (meme mecanisme de persistance, meme objet dict partage).
PIEGES DEJA RENCONTRES sur cette fonctionnalite (a ne pas refaire) :
    - Un ui.select seul en mode combo box Quasar (props use-input +
      new-value-mode="add-unique") a ete essaye en premier pour a la fois
      choisir dans une liste ET taper une valeur hors liste dans le meme
      widget : ne fonctionne pas de facon fiable (le wrapper NiceGUI/
      QSelect tend a re-contraindre la valeur aux options connues).
    - Un ui.input + <datalist> HTML natif a ensuite ete essaye (texte
      libre garanti + suggestions cliquables) : fonctionnellement
      correct, mais rejete par l'utilisateur au profit du design a deux
      lignes separees ci-dessus (comportement explicitement demande).
La valeur courante de chaque champ est incluse dans le payload a chaque
play/update_data (pas de capture "une seule fois" comme bib_on/target_on).
Les champs sont desactives (widget.disable()) des que l'etat n'est plus
idle, et reactives au retour a idle (stop, reset_to_idle) - evite de
changer une valeur pendant que le graphique est deja affiche.

Bouton "intermediaire" (intermediate_on=True, intermediate_type="shoot_out"
/ "slope" / "relay", field_intermediate="timekey" par defaut) : combo box
(ui.select) affichee SOUS le bouton, listant les intermediaires
ACTUELLEMENT en course pour ce type, calcules par
_current_intermediate_options() a partir de data.config.interorder (voir
biathdata_reference.txt section 1 : liste ordonnee des noms de cles
reellement utilises par CETTE course - contient aussi C_RELAY1/2/3 si et
seulement si le format de course actuel en est un) filtree par prefixe
("shoot_out" -> "C_INTERSHOOT", "slope" -> "C_INTERSLOPE", "relay" ->
"C_RELAY" ; attention "C_INTERSHOOT".startswith exclut bien
C_INTERINSHOOT*, prefixe different malgre la ressemblance). CORRECTION
D'UNE ERREUR PRECEDENTE : "relay" a d'abord ete implemente avec une liste
FIXE C_RELAY1..3 codee en dur (en supposant, a tort, que interorder ne
contenait jamais de cles C_RELAY) - corrige suite a une remarque directe
de l'utilisateur : interorder PEUT contenir C_RELAY1/2/3 si le format de
course en est un, donc "relay" utilise le meme filtrage dynamique que les
deux autres types, pas de cas particulier dans le code.
_refresh_intermediate_options(), sur un ui.timer(1.0, ...) propre a chaque
bouton intermediate_on, resynchronise la liste d'options en direct (utile
car le websocket se connecte APRES la construction de l'interface -
data.config peut valoir None au demarrage) et reinitialise la selection
si elle n'est plus valide. EN PLUS de ce polling (jusqu'a 1s de latence),
_refresh_intermediate_options() est aussi appelee INSTANTANEMENT des
qu'un nouveau message websocket complet arrive, via
BiathDataWebsocket.on_message() (voir plus bas "Rafraichissement instantane
sur nouvelle donnee") - utile si le logiciel de donnees demarre APRES ce
logiciel, le tout premier message pouvant arriver a n'importe quel moment.
La valeur choisie est poussee immediatement via
update_template si le graphique est deja affiche (pas de capture "au
premier play" ici, contrairement a bib_on/target_on - changer
d'intermediaire en direct est le but recherche). Tant qu'aucun
intermediaire n'est choisi, _build_payload bloque le play/l'update (renvoie
None, notifie l'operateur) - verifie EN PREMIER, avant meme de demander le
dossard (bib_on), pour ne pas faire perdre ce travail a l'operateur si
l'intermediaire s'avere manquant ensuite.

Restriction par format de course (race_formats=["PURSUIT", ...], optionnel,
None par defaut) : _is_format_available() compare data.event_infos
.RACEFORMAT (voir biathdata_reference.txt section 2, ex: "MASSSTART") a
cette liste. Si le format actuel n'y figure pas, TOUT le bouton devient
inutilisable - _refresh_appearance() le grise entierement (bg-slate-300,
cursor-not-allowed, label en slate-500, survol IN/OUT force invisible/
pointer-events-none) ET _on_main_click/_on_hover_click/_on_next_page/
_on_prev_page retournent immediatement sans effet (double protection :
visuelle + logique). Une icone "block" grise apparait a cote du bouton
(meme emplacement que l'icone de connexion) avec un tooltip expliquant le
format actuellement detecte. _refresh_format_availability(), sur un
ui.timer(1.0, ...) propre a chaque bouton race_formats, revalidate chaque
seconde (le format peut n'etre connu qu'apres coup, meme raison que pour
intermediate_on) - et, comme _refresh_intermediate_options, EGALEMENT
appelee instantanement sur reception d'un nouveau message (voir plus bas).
Omettre race_formats (None) = bouton actif pour tous les
formats, comportement inchange par rapport a avant cette fonctionnalite.

Restriction par sexe/categorie (restrict_to_sex/restrict_to_cat, field_sex
="sexe"/field_cat="cat" par defaut, tous optionnels/False) : mecanisme en
2 parties, un etat GLOBAL + un opt-in par bouton.
    - Etat GLOBAL (SceneButton._restrict_by_sex/_restrict_by_cat, bool) :
      2 cases a cocher PLACEES DANS LE CORPS DE PAGE (pas le header) via
      templates.json ("_restrict_controls": true, voir buttons_config.py/
      interface.add_restrict_controls) - positionnement libre choisi par
      l'operateur (section/column ; PAS de "row", TOUJOURS tout en haut de
      la colonne - voir 6.2), comme un titre de colonne ou un bouton.
      Persiste dans config.json (contrairement au reste de l'etat
      en direct d'un bouton). set_restrict_by_sex(value)/
      set_restrict_by_cat(value) (classmethods async) sont les SEULS
      points d'entree pour changer cet etat : ils l'appliquent, rafraichissent
      la visibilite des combo box de CHAQUE bouton concerne (voir plus bas),
      et repoussent IMMEDIATEMENT (_update_data()) le payload de tout
      bouton restrict_to_sex/cat=true deja a l'ecran (bib_on ou non - voir
      correction "Opt-in par bouton" ci-dessous, la case globale seule ne
      suffit plus a concerner un bib_on) - exactement le meme principe
      "d'application instantanee sans redemarrage" que le reste des
      Parametres.
    - Regroupement des categories (SceneButton._category_groups, liste de
      listes, ex: [["U15"], ["U17"], ["U19"], ["U21", "SEN"]]) : les 5
      categories FIXES (app_config.CATEGORIES = U15/U17/U19/U21/SEN, pas
      configurables) peuvent etre regroupees ARBITRAIREMENT - autant de
      categories que voulu dans un meme groupe, pas limite a des paires -
      en GLISSER-DEPOSER dans la boite de dialogue Parametres (voir 6.1
      pour le detail d'implementation SortableJS). set_category_groups
      (groups) (classmethod async, appelee par le callback on_end du
      glisser-deposer, PAS par on_settings_save - application/persistance
      instantanee a chaque deplacement) rafraichit les options de CHAQUE
      combo box categorie deja construite (voir _refresh_restrict_cat_
      options, meme principe que _refresh_intermediate_options : preserve
      la selection si toujours valide, "ALL" sinon) et repousse
      immediatement le payload des boutons affectes SI restrict_by_cat est
      actuellement actif (sinon le regroupement n'a aucun effet visible,
      inutile de repousser). app_config.normalize_category_groups(groups)
      garantit une partition VALIDE des CATEGORIES (chacune dans
      exactement un groupe) a chaque lecture - necessaire car
      category_groups est une structure libre (potentiellement modifiee/

      propre groupe, doublon/categorie inconnue -> ignore (bug reel

      n'etait pas filtre par une premiere version qui mettait a jour
      `seen` en bloc apres coup plutot qu'entree par entree).

      PAIRE (app_config.CATEGORY_PAIRS, "category_group_links":
      {"CAT_A|CAT_B": bool}, resolues en groupes via une union-find),
      validees par le bouton "Enregistrer" comme le reste des Parametres -

      l'utilisateur ("je veux pouvoir creer des groupe en glissant

      present dans un config.json existant (et l'absence du nouveau) et le

      attendre que l'operateur rouvre Parametres. PIEGE EVITE lors de

      deja fusionne avec DEFAULT_CONFIG (qui contient TOUJOURS
      "category_groups" via ses valeurs par defaut, meme si le fichier ne
      l'a pas) - sinon la migration ne se declenche jamais.
    - Opt-in par bouton - DEUX conditions doivent etre reunies pour qu'un
      champ sexe/categorie soit envoye : restrict_to_sex/restrict_to_cat
      dans le JSON de CE bouton ET la case a cocher globale correspondante.
      CORRECTION REELLE (design initial rejete par l'utilisateur) : la
      toute premiere version rendait un bib_on automatiquement/
      inconditionnellement concerne des que la case globale etait cochee
      (aucun reglage JSON possible/necessaire pour lui). L'utilisateur a
      corrige explicitement : "je t'avais dit que tous les boutons avec
      bib_on devaient... l'activer avec les champs dans le json" - un
      bib_on doit desormais LUI AUSSI activer restrict_to_sex/
      restrict_to_cat explicitement, un bib_on qui ne les active pas
      n'est JAMAIS concerne, meme case globale cochee. Les classmethods
      set_restrict_by_sex/set_restrict_by_cat/set_category_groups ont ete
      corrigees en consequence (le test "button.bib_on or button.
      restrict_to_sex" est devenu simplement "button.restrict_to_sex" -
      bib_on n'est plus un raccourci qui contourne le reglage JSON). Les 2
      cas restent neanmoins differents dans leur RENDU (combo box ou non) :
        1) bib_on=true + restrict_to_sex/restrict_to_cat=true : PAS de
           combo box (ce bouton connait deja l'athlete selectionne). Quand
           la case globale correspondante est AUSSI active, _build_payload
           calcule directement sexe/categorie depuis data.timing_data
           [bib] (_athlete_sex_value/_athlete_cat_value) : C_SEX (1=homme
           ->"H", 2=femme->"D", confirme par l'utilisateur - biathdata_
           reference.txt ne confirmait que la valeur homme) et C_CATEGORY
           resolue vers son GROUPE (jointe par ";", ex: athlete "U21"
           regroupe avec SEN -> "U21;SEN"). Athlete/valeur introuvable ->
           pas de restriction ("HD"/"ALL"), JAMAIS une valeur devinee a
           tort.
        2) bib_on=false + restrict_to_sex/restrict_to_cat=true : affiche
           sous le bouton une combo box (Hommes/Dames/Hommes et Dames pour
           le sexe ; "Toutes categories" + un groupe par entree de
           _category_groups pour la categorie, valeur envoyee = categories
           du groupe jointes par ";", libelle affiche = jointes par " + ")
           - MASQUEE (via _sex_row/_cat_row.visible) tant que la case
           globale correspondante n'est pas active (_refresh_restrict_
           visibility). Contrairement aux free_texts (verrouilles pendant
           l'affichage), ces combo box restent modifiables en direct et
           repoussent immediatement (meme principe que intermediate_on) :
           changer d'antenne pendant l'affichage est le but recherche,
           pas une valeur figee au premier play.
        3) restrict_to_sex/restrict_to_cat=false (defaut) : ce bouton n'est
           JAMAIS concerne, quel que soit l'etat des cases globales -
           bib_on ou non, INCHANGE par la correction ci-dessus.
    _build() : has_restrict_selects = not bib_on and (restrict_to_sex or
    restrict_to_cat) determine si ce bouton a besoin d'une box englobante
    (au meme titre que bib_on/target_on/intermediate_on/free_texts) - ce
    calcul n'a pas change (seule la condition d'ENVOI du champ dans
    _build_payload a change, pas celle d'affichage de la combo box, deja
    correcte des le depart).

Rafraichissement instantane sur nouvelle donnee (BiathDataWebsocket.
on_message()/remove_listener(), SceneButton._subscribe_to_new_data()) :
au-dela du polling ui.timer(1.0, ...) deja en place pour les intermediaires
et les formats de course (jusqu'a 1s de latence, largement suffisant en
soi, mais quand meme perceptible), _handle_message() (biathdata_ws.py)
notifie desormais une liste d'abonnes (callbacks synchrones sans argument)
CHAQUE fois qu'un nouveau message complet (config+event_infos+timing_data)
est traite avec succes - permet a l'UI de se rafraichir DES la reception,
sans attendre le tick suivant. Un abonne qui leve une exception ne casse
JAMAIS la boucle de reception (try/except autour de chaque callback,
traceback affiche en console) - un bug d'affichage sur un bouton ne doit
jamais empecher la reception des DONNEES suivantes pour tous les autres.
PIEGE EVITE (pas un bug rencontre, anticipe des la conception) :
BiathDataWebsocket est un SINGLETON partage par tous les clients/pages
(un seul `data` en module-level dans main.py), alors que SceneButton est
RECREE a chaque chargement de page (build_body s'execute par client). Un
abonnement direct sans nettoyage accumulerait donc un callback
supplementaire dans le registre PARTAGE a chaque rechargement de l'onglet
navigateur, sans jamais retirer les anciens (fuite memoire + callbacks
essayant de mettre a jour des elements deja detruits cote client,
indefiniment). SceneButton._subscribe_to_new_data() evite ca en enregistrant
AUSSI un ui.context.client.on_delete(...) qui desabonne automatiquement
le callback quand CE client precis (cet onglet) est definitivement ferme.
Utilise pour intermediate_on et race_formats ; le polling ui.timer reste
en place dans les deux cas (filet de securite, coherent avec le pattern
deja etabli ailleurs dans le fichier - connexion, etc.).

Second CG (second_cg=<nom de template>, second_cg_layer=None par defaut) :
declare un DEUXIEME graphique joue/stoppe/mis a jour EN MEME TEMPS que le
template principal, sur le meme channel. IMPORTANT : second_cg_layer est
un LAYER VIDEO (comme "layer" pour le principal), PAS un cg_layer
d'empilement CG - omis, le second CG joue sur le MEME layer video que le
principal (self.layer) ; precise, il joue sur CE layer video a lui, 2
producers CasparCG totalement independants (donc visibles comme 2 layers
distincts dans une INFO AMCP, par exemple). L'index d'empilement interne
(parametre "cg_layer" de la commande AMCP CG ADD) est calcule par
_second_cg_stack_layer() = self.cg_layer + 1 (TOUJOURS distinct de
self.cg_layer, voir bug 3 de l'HISTORIQUE ci-dessous pour la raison).
HISTORIQUE (4 iterations avant la version finale ci-dessus, a ne pas
reproduire) :
    1) D'abord, second_cg_layer a ete implemente comme le cg_layer du
       second CG (les deux graphiques restant sur le MEME layer video que
       le principal, juste empiles differemment). Rejete par l'utilisateur
       apres verification des logs AMCP reels : les deux CG ADD
       montraient bien la MEME adresse "channel-layer" (ex: "2-20"), ce
       qui n'etait pas le comportement voulu.
    2) Ensuite, un parametre SEPARE "second_layer" a ete ajoute pour
       controler le layer video, en gardant "second_cg_layer" pour le
       cg_layer d'empilement. Rejete aussi : l'utilisateur avait deja
       utilise "second_cg_layer" dans son JSON en s'attendant a ce que CE
       nom precis controle le layer video (coherent avec sa toute
       premiere demande : "secondcg et second cg layer... pour indiquer
       un deuxieme graphique"). D'ou la version finale : un seul
       parametre, "second_cg_layer", qui EST le layer video.
    3) Une fois "second_cg_layer" fixe comme layer video, l'index
       d'empilement CG du second CG reutilisait encore self.cg_layer (le
       MEME que le principal). Ca fonctionnait en direct au programme,
       mais pas en passant par le preview au prealable ("ca marche bien
       quand je l'envoie directement au pgm mais pas quand je passe au
       prw d'abord"). Cause : format_address("prw", layer) (voir 4.3)
       IGNORE le layer fourni et force TOUJOURS channel_preview-1 pour
       TOUS les boutons - donc en preview, le principal et le second CG
       visent la MEME adresse "channel-layer". Avec le MEME cg_layer en
       plus, les deux CG ADD visaient exactement le meme
       (adresse, cg_layer) : CasparCG remplace en place le producer
       existant sur un CG ADD vers un (adresse, cg_layer) deja occupe (pas
       besoin d'un REMOVE explicite) - le second CG ADD ecrasait donc
       silencieusement le principal, qui disparaissait du preview. Fixe en
       ajoutant _second_cg_stack_layer() = self.cg_layer + 1 (toujours
       distinct de self.cg_layer), utilise comme argument cg_layer= dans
       les 4 points d'appel du second CG au lieu de self.cg_layer.
    4) Meme apres le fix precedent (cg_layer distinct en preview, donc les
       DEUX producers coexistent bien visuellement en preview), le Take
       restait casse : au Take, c'est le SECOND CG qui apparaissait au
       programme, et le template PRINCIPAL disparaissait purement et
       simplement (logs AMCP confirmes par l'utilisateur : apres les 2 CG
       ADD en preview attendus, le Take n'envoyait au programme qu'un
       "CG <adr> ADD 2 shootingrange" - jamais le template principal).
       Cause reelle : CasparCG._preview (casparcg.py) etait un slot
       UNIQUE pour toute l'appli (pas par bouton, pas par cg_layer) -
       play_template() l'ecrasait a chaque play reussi vers "prw", sans
       distinction. _play_second_cg() jouant le second CG EN PREVIEW juste
       apres le principal (dans _play()), il ecrasait systematiquement le
       suivi du principal avec ses propres infos (template="shootingrange",
       cg_layer=second). play_prw_to_pgm(), appele par _take() pour
       reprendre le principal, rejouait donc a chaque fois le SECOND CG
       (avec le mauvais cg_layer en plus) a la place du principal, qui
       n'etait jamais envoye au programme. Fixe en transformant
       CasparCG._preview en dict{cg_layer: {...}} (un slot par cg_layer
       au lieu d'un slot unique), et en donnant a play_prw_to_pgm(layer,
       cg_layer) un parametre cg_layer explicite pour choisir LEQUEL des
       producers previewes reprendre - _take() lui passe desormais
       cg_layer=self.cg_layer (celui du principal), le second CG restant
       rejoue separement comme avant via self._second_cg_payload.
_second_cg_video_layer() est la seule fonction qui calcule ce layer
effectif (second_cg_layer si precise, sinon self.layer), appelee partout
ou le second CG est vise (_play_second_cg, _take, _stop, _update_data) -
une seule source de verite plutot que de dupliquer le ternaire a chaque
appel. Points d'implementation :
    - _play_second_cg(channel, payload), appelee juste apres le succes du
      play principal dans _play() : joue le second CG, et EN PREVIEW
      seulement, memorise le payload dans self._second_cg_payload. Pour
      le channel "prw", format_address() ignore de toute facon le layer
      fourni et force toujours channel_preview-1 (voir 4.3) : la
      distinction second_cg_layer/self.layer ne compte donc reellement
      que pour le programme.
    - _take() appelle play_prw_to_pgm(self.layer, cg_layer=self.cg_layer)
      pour le principal (voir point 4 de l'HISTORIQUE - cg_layer precise
      quel producer previewe reprendre parmi ceux suivis par
      CasparCG._preview), PUIS rejoue le second CG a la main vers le
      programme avec le payload memorise dans self._second_cg_payload :
      play_prw_to_pgm() ne reprend qu'UN cg_layer a la fois, jamais les
      deux automatiquement, donc le second CG doit toujours etre rejoue
      separement par SceneButton.
    - _stop() stoppe (CG STOP, meme animation de sortie) le second CG en
      meme temps que le principal ; _update_data() pousse le meme payload
      aux deux (et rafraichit self._second_cg_payload si en preview) ;
      reset_to_idle() efface self._second_cg_payload.
    - Echec du second CG (play/take/stop/update) : notifie une erreur
      mais NE FAIT JAMAIS echouer l'action sur le template principal
      (deja reussie a ce stade) - mieux vaut le graphique principal seul
      qu'un echec total. Meme philosophie que le reste du fichier (stop()
      qui echoue sur un STOP secondaire ne doit pas bloquer l'operateur).

Un seul occupant a la fois par slot CasparCG, MAIS preview et programme
suivent desormais exactement la MEME regle (multi-slot preview, voir
8.11 pour l'historique du changement) :
    - Preview : chaque bouton previse sur SON PROPRE (layer, cg_layer) -
      SceneButton._active_preview est un dict indexe par (layer, cg_layer),
      comme _active_pgm. Plusieurs boutons DIFFERENTS peuvent donc etre en
      preview SIMULTANEMENT (chacun sur son propre layer), permettant de
      pre-composer plusieurs graphiques avant de tous les envoyer au
      programme d'un coup. Mettre un bouton en preview clear() (immediat,
      sans animation) SEULEMENT son propre (layer, cg_layer) et remet a
      idle (reset_to_idle()) le bouton qui l'occupait avant - les autres
      slots de preview ne sont pas touches (SceneButton._claim_preview).
    - Programme : un (layer, cg_layer) donne ne peut avoir qu'un seul
      occupant (SceneButton._active_pgm, dict indexe par (layer,
      cg_layer)). Si un bouton est envoye au programme (play direct ou
      Take) sur le meme (layer, cg_layer) qu'un bouton deja a l'antenne,
      ce dernier est stoppe (stop(), meme mecanisme que le bouton "OUT"
      manuel, avec l'auto-remove differe habituel) avant le chargement du
      nouveau.
    - SceneButton.reset_all() (utilise par l'Emergency All Out, voir
      build_header) remet TOUS les boutons a idle et vide ces deux
      registres.
    - SceneButton.stop_all_pgm() (async, utilise par le bouton ALL OUT du
      footer, voir build_footer) stoppe tous les boutons actuellement au
      programme (appelle button._stop() sur chacun, meme mecanisme que le
      survol "OUT"), sans toucher a la preview.
    - SceneButton.clear_all_previews() (async, utilise par le bouton CLEAR
      PRW du footer) clear cote CasparCG CHAQUE layer de preview
      actuellement suivi comme actif (le layer principal de chaque bouton
      en preview, plus celui de son second_cg s'il est distinct), puis
      remet chacun de ces boutons a idle - contrairement a l'ancien design
      (un seul layer de preview partage, toujours clearable a l'aveugle),
      ne clear QUE ce qui est suivi localement (un vrai desync, ex: apres
      un redemarrage du process, necessite plutot emergency_all_out()).
    - SceneButton.take_all_previews() (async, utilise par le bouton TAKE
      PREVIEW du footer) fait un Take (_take()) sur CHAQUE bouton
      actuellement en preview, pas un seul - "envoyer plusieurs graphiques
      pre-composes au programme en meme temps" est le but explicite du
      multi-slot.
    - SceneButton.swap_preview_pgm() (async, utilise par le bouton SWAP du
      footer) fait la meme chose que take_all_previews(), mais renvoie EN
      PLUS en preview le graphique au programme echange avec chaque
      preview (capture de son payload AVANT de le stopper). BUG REEL
      RENCONTRE ET CORRIGE : apparier preview/pgm par (layer, cg_layer)
      IDENTIQUE (comme _active_pgm/_active_preview sont indexes) ne
      marche presque jamais en pratique, un swap se faisant normalement
      entre deux boutons DIFFERENTS (types de graphiques differents, donc
      layers differents) - resultat, le graphique au pgm restait en place
      au lieu de repartir en preview. Corrige avec un appariement en 2
      passes : d'abord un eventuel appariement EXACT par (layer,
      cg_layer) (cas rare), puis les preview/pgm restants sont apparies
      dans l'ordre - sans ambiguite avec un seul graphique de chaque cote
      (usage typique). Un preview sans pgm a echanger est simplement pris.
      AUTRE BUG REEL RENCONTRE ET CORRIGE : le second_cg de l'ancien
      pgm_button (voir "Second CG" plus bas) n'etait pas renvoye en
      preview, seul le template principal l'etait - le second_cg
      disparaissait donc silencieusement, et _second_cg_payload restant
      vide (efface par _stop()), un swap/Take suivant sur ce meme bouton
      ne le rejouait plus jamais au programme. Corrige en renvoyant aussi
      le second_cg en preview (meme payload, sur son propre layer/
      cg_layer) et en remettant a jour pgm_button._second_cg_payload.

Logs console (stdout) : SceneButton._log(message) affiche une ligne

8. LECONS / PIEGES NICEGUI DECOUVERTS PENDANT LE DEVELOPPEMENT
------------------------------------------------------------------

Ces points ont coute du temps de debogage et doivent etre gardes en tete
pour la suite du developpement de l'interface :

8.1 .classes(replace=...) remplace TOUTES les classes, y compris celles
    posees par defaut par NiceGUI/Quasar (ex: la classe "flex" implicite
    d'un ui.row()). Oublier de la reinclure casse silencieusement le
    layout (ex: une icone qui ne reste plus sur la meme ligne qu'un
    texte). Toujours reinclure explicitement "flex" (et tout autre
    classe de base necessaire) dans la string de remplacement.

8.2 ui.button(..., color=None) est necessaire pour desactiver la couleur
    "primary" (bleue) que Quasar applique par defaut aux boutons ; sinon
    les classes Tailwind de couleur (text-*, bg-*, border-*) sont
    silencieusement ignorees/ecrasees.

8.3 ui.image(source) : passer un pathlib.Path (pas une simple string) est
    necessaire pour que NiceGUI reconnaisse un fichier local et le serve
    automatiquement via une route interne. Une string est envoyee telle
    quelle comme attribut src au navigateur (resolue relativement a
    l'URL de la page, pas au filesystem serveur -> 404 silencieux). Voir
    aussi : dimensionner avec des tailles fixes (h-10 w-16) plutot que
    w-auto, qui peut mal se comporter avec le composant Quasar QImg
    sous-jacent.

8.4 Pour un focus fiable dans une ui.dialog(), combiner
    .props("autofocus") ET un ui.timer(0.1, lambda: el.run_method
    ("focus"), once=True) de secours (l'autofocus HTML seul est parfois
    rate a cause de l'animation d'ouverture de Quasar).

8.5 PIEGE MAJEUR - "auto-index page" : si du code NiceGUI est ecrit au
    niveau module (en dehors d'une fonction decoree @ui.page), NiceGUI le
    re-execute INTEGRALEMENT (y compris de simples assignations Python
    comme la creation d'instances CasparCG/BiathDataWebsocket) a CHAQUE
    nouvelle connexion/reconnexion de client navigateur. Consequence
    reelle rencontree : des instances caspar/data toutes neuves (jamais
    connectees) etaient recreees a chaque chargement de page, rendant
    orphelines celles connectees dans @app.on_startup - l'interface
    affichait donc "deconnecte" en permanence alors que la connexion
    reelle fonctionnait tres bien en arriere-plan. SOLUTION APPLIQUEE :
    creer les instances caspar/data au vrai niveau module (une seule
    fois, avant tout ui.run()), et envelopper toute la construction de
    l'UI dans une fonction @ui.page("/") qui, elle, peut etre re-executee
    par client sans consequence puisqu'elle ne fait que REFERENCER les
    objets globaux existants. Diagnostic : comparer id(caspar)/id(data)
    entre le point de connexion et le point d'affichage a permis de
    confirmer le probleme.

8.6 reload=False dans ui.run() est garde par prudence/bonne pratique pour
    une appli avec des connexions/taches de fond persistantes (evite les
    complications potentielles du sous-processus de rechargement de
    uvicorn/NiceGUI), meme si ce n'etait PAS la cause reelle du bug 8.5.

8.7 ui.dialog() utilise en `valeur = await dialog` ouvre automatiquement
    la boite de dialogue et suspend jusqu'a dialog.submit(valeur) - motif
    pratique pour des flux de saisie modale (utilise pour bib_on et
    target_on).

8.8 PIEGE - une grille "ligne/colonne" faite de plusieurs ui.row()
    flex-wrap independantes (une par ligne) NE PRODUIT PAS un alignement
    de colonnes entre les lignes. Chaque ui.row() flex est son propre
    contexte : "colonne N" n'y designe que le N-ieme enfant de CETTE ligne
    precise, base sur son propre contenu, sans lien avec les autres
    lignes. Consequence reelle rencontree (interface.build_body) : un
    bouton place en (row=2, column=5) apparaissait juste apres celui en
    (row=2, column=1) au lieu de s'aligner sous la colonne 5 de la ligne 1,
    car la ligne 2 n'avait que 2 boutons (donc 2 "cases" flex, pas 5).
    SOLUTION APPLIQUEE : conteneur de section en display:grid (Tailwind
    "grid"), chaque case etant un ui.column positionne explicitement via
    le style CSS `grid-row: N; grid-column: M;`. Une vraie grille CSS
    partage ses pistes de colonnes entre toutes les lignes, donc la
    colonne M s'aligne verticalement partout, quel que soit le nombre
    d'entrees des autres lignes.

8.9 PIEGE - ui.header()/ui.footer() (QHeader/QFooter Quasar) sont
    positionnes plein-largeur par rapport au VIEWPORT par defaut,
    independamment du padding applique au conteneur de contenu de page
    (.nicegui-content, qui a un padding par defaut non nul). Consequence
    reelle rencontree : le header, indente uniquement via son propre m-3,
    et le corps de page (build_body), indente via son propre px-3 MAIS
    A L'INTERIEUR du padding par defaut de .nicegui-content, ne
    s'alignaient pas horizontalement - le corps apparaissait plus
    indente que le header.
    SOLUTION APPLIQUEE (build_header) :
    ui.query(".nicegui-content").style("padding-left: 0; padding-right: 0;")
    pour ramener le corps de page au meme repere horizontal (le viewport)
    que le header/footer, puis chaque conteneur (header m-3, corps px-3,
    footer m-3) reproduit lui meme le meme inset de 12px pour rester
    visuellement aligne. Utiliser .style() et non .classes(replace=...)
    ici, pour ne pas casser d'eventuelles classes flex/gap internes de
    NiceGUI sur cet element (meme categorie de piege que 8.1).
    PIEGE DANS LE PIEGE (regression reelle rencontree et corrigee) : la
    toute premiere version de ce correctif utilisait
    ui.query(".nicegui-content").style("padding: 0;") (les 4 cotes, pas
    seulement gauche/droite). Or Quasar calcule DYNAMIQUEMENT un
    padding-top sur ce meme element .nicegui-content pour pousser le
    contenu sous le QHeader (positionne en "fixed", donc superpose au
    contenu par defaut sans ce decalage). Mettre "padding: 0" ecrasait
    aussi ce padding-top -> le corps de page (build_body) se retrouvait
    affiche SOUS/DERRIERE le header au lieu d'etre entre le header et le
    footer. D'ou la version finale ci-dessus, qui ne touche QUE
    padding-left/padding-right et laisse Quasar gerer padding-top/bottom.

8.10 TECHNIQUE - reduire toute une zone de l'UI (boutons, texte, grilles...)
    sans retoucher chaque classe Tailwind individuellement : propriete CSS
    "zoom" (pas transform:scale, qui ne modifie pas la taille de boite
    dans le flux et provoquerait un chevauchement avec les elements
    suivants). Utilise dans interface.build_body via BODY_ZOOM (0.8 par
    defaut, seule valeur a modifier pour retoucher la taille globale) sur
    le conteneur du corps de page uniquement (header/footer non concernes,
    en dehors de ce conteneur). PIEGE associe : zoom retrecit aussi la
    boite de l'element dans le flux normal (contrairement a
    transform:scale) - une hauteur fixe (ex: h-[calc(100vh-190px)]) doit
    donc etre compensee (divisee par BODY_ZOOM) AVANT le zoom pour que la
    hauteur RENDUE, une fois le zoom applique, reste correcte (sinon un
    vide apparait avant le footer). "zoom" est un standard CSS relativement
    recent avec un support navigateur bon mais pas universel (Firefox
    seulement depuis mi-2024) - a garder en tete si l'appli doit un jour
    tourner sur un navigateur different de Chrome/Edge.

8.11 PIEGE MAJEUR / CHANGEMENT DE DESIGN - la preview a longtemps ete un
    UNIQUE layer CasparCG partage par TOUS les boutons (format_address()
    forcait "prw" a toujours cibler channel_preview-1, quel que soit le
    layer passe). Ca a cause 2 bugs reels distincts avant d'etre change :
      1) Le second CG d'un bouton (voir "Second CG" en section 7),
         empile au-dessus du principal (cg_layer+1) sur ce meme layer
         unique, le RECOUVRAIT visuellement des que son template n'etait
         pas transparent sur toute la surface - seul le second CG restait
         visible en preview ("seulement le second cg est affiche dans le
         preview").
      2) CasparCG._preview (casparcg.py) etait lui-meme un slot UNIQUE
         pour toute l'appli (pas par bouton), ecrase par CHAQUE play()
         reussi vers "prw" - jouer le second CG en preview juste apres le
         principal effacait donc le suivi du principal, et le Take
         reprenait le SECOND CG a la place du principal (voir HISTORIQUE
         point 4 de la section "Second CG" en 7).
    Plutot que rafistoler ces 2 symptomes independamment, le design a ete
    change a la racine, a la demande explicite de l'utilisateur : la
    preview suit maintenant EXACTEMENT la meme regle que le programme -
    chaque bouton previse sur SON PROPRE (layer, cg_layer), comme au
    programme (format_address() exige desormais un layer explicite pour
    "prw" ET "pgm", plus de cas special). Consequences :
      - CasparCG._preview est passe de dict{cg_layer: {...}} (deja
        corrige une fois, voir HISTORIQUE point 4 en section 7) a
        dict{(layer, cg_layer): {...}} - un slot par layer ET cg_layer.
      - clear(channel="prw", layer=X) ne vide plus tout le suivi
        _preview, seulement les entrees dont le layer == X (les autres
        boutons en preview sur d'autres layers ne sont plus impactes).
      - play_prw_to_pgm(layer, cg_layer) cible desormais un (layer,
        cg_layer) precis au lieu d'un cg_layer seul.
      - SceneButton._active_preview est passe de "un seul bouton (ou
        None)" a dict[(layer, cg_layer), SceneButton] - meme forme que
        _active_pgm.
      - CONSEQUENCE PRODUIT VOULUE : plusieurs boutons DIFFERENTS peuvent
        desormais etre en preview SIMULTANEMENT (chacun sur son propre
        layer), ce qui permet de PRE-COMPOSER plusieurs graphiques avant
        de tous les envoyer au programme d'un coup - c'est le but
        explicite de ce changement, pas un effet de bord. Les boutons
        CLEAR PRW / TAKE PREVIEW / SWAP du footer ont ete adaptes en
        consequence pour agir sur TOUS les slots de preview actifs au
        lieu d'un seul (voir SceneButton.clear_all_previews/
        take_all_previews/swap_preview_pgm, section 7).
      - _take() doit desormais explicitement clear() le layer de preview
        du second CG s'il differe du layer principal (play_prw_to_pgm ne
        clear que self.layer) - sinon il resterait visible en preview
        alors qu'il est deja repris au programme.
    A NE PLUS FAIRE : revenir a un design "un seul layer de preview
    partage" pour "simplifier" - c'est precisement la source des 2 bugs
    ci-dessus, et la pre-composition multi-graphiques est une fonctionnalite
    explicitement demandee, pas un detail d'implementation.

8.12 PIEGE MAJEUR - element.make_sortable() (SortableJS, *NiceGUI 3.11+*)
    NE FONCTIONNE PAS a l'interieur d'un contenu TELEPORTE par Vue -
    concretement, ni dans un ui.dialog() (QDialog), ni dans un ui.menu()
    (QMenu). Rencontre en implementant le glisser-deposer du regroupement
    des categories (voir section 7 "Restriction par sexe/categorie") :
    l'utilisateur rapportait "je ne peux pas deplacer les categories...
    ca selectionne le texte", puis apres un premier correctif (select-none,
    necessaire mais insuffisant, voir plus bas) "ca ne marche toujours pas
    je n'arrive pas a les drag and drop malgres que l'icone du pointeur me
    dit que je peux le faire" - symptome qui a demande une INVESTIGATION
    APPROFONDIE (protocole DevTools de Chrome, evenements souris simules
    "trusted" via Input.dispatchMouseEvent - indiscernables d'une vraie
    souris - pour eliminer un simple probleme de simulation de test) avant
    de trouver la vraie cause.

    SYMPTOME PRECIS : aucune erreur JS (verifie via Runtime.exceptionThrown/
    Log.entryAdded sur toute la duree du chargement de page), le module
    "nicegui-sortable" s'importe sans probleme, Sortable.create() reussit
    (renvoie une instance non-nulle, testable manuellement via
    Runtime.evaluate), mais le glisser-deposer ne se declenche JAMAIS -
    verifie avec une vraie sequence mousePressed/mouseMoved (par petits pas,
    avec delais)/mouseReleased. Le curseur CSS (cursor-move) s'affiche
    normalement au survol (raison du "l'icone me dit que je peux le
    faire" rapporte par l'utilisateur) car c'est un pur effet CSS, sans
    rapport avec le fonctionnement reel du JS.

    PISTES ELIMINEES UNE PAR UNE (chacune testee empiriquement, aucune n'a
    resolu le probleme) :
        1) select-none manquant sur les puces -> CORRIGE (necessaire,
           piege reel independant : sans lui, un mousedown-drag sur le
           TEXTE d'une puce est intercepte par le navigateur comme une
           selection de texte plutot que de declencher SortableJS -
           select-none seul suffit HORS d'un dialogue/menu, voir plus bas)
           mais PAS suffisant a lui seul pour le probleme rapporte ensuite.
        2) Timing/DOM pas encore rendu - repousser make_sortable() a la
           premiere ouverture confirmee du dialogue (dialog.on_value_change)
           + un delai supplementaire de 300ms (ui.timer) : AUCUN EFFET.
        3) Mode "fallback" force (options={"forceFallback": True}, evite
           l'API HTML5 drag native au profit d'un suivi souris JS pur, au
           cas ou le natif serait bloque par le modal) : AUCUN EFFET.
        4) Prop Quasar "seamless" sur le dialogue (retire completement le
           comportement modal/backdrop) : AUCUN EFFET.
        5) ui.menu() a la place de ui.dialog() (composant Quasar different,
           avec une logique d'evenements differente - eliminait une cause
           SPECIFIQUE a QDialog comme un gestionnaire "clic exterieur pour
           fermer") : MEME ECHEC.

    CAUSE REELLE IDENTIFIEE (par elimination + comparaison controlee) :
    le POINT COMMUN entre ui.dialog() et ui.menu() (tous deux casses) est
    que Quasar rend leur contenu via le <Teleport> de Vue (deplace
    ailleurs dans le DOM - typiquement vers document.body - que sa
    position logique dans l'arbre de composants). Une simple ui.column
    basculee par .visible (PAS de Teleport) avec EXACTEMENT le meme code
    de glisser-deposer (meme sans aucun des correctifs 2-4 ci-dessus, y
    compris SANS delai) fonctionne PARFAITEMENT du premier coup - verifie
    plusieurs fois de suite avec le meme protocole de test. make_sortable()
    est donc incompatible avec du contenu teleporte, pour une raison non
    identifiee avec certitude au niveau du mecanisme exact (hypothese : le
    controleur Sortable invisible est place via `with self.client.layout:`
    - donc PAS teleporte, TOUJOURS enfant "normal" de l'arbre - alors que
    l'element qu'il pilote, LUI, peut l'etre ; un decalage entre ID DOM et
    resolution d'evenements/coordonnees pourrait en decouler, mais ce n'est
    pas confirme au niveau du code source de nicegui-sortable/SortableJS).

    SOLUTION RETENUE : ne JAMAIS mettre du contenu avec make_sortable() a
    l'interieur d'un ui.dialog()/ui.menu(). Le panneau de regroupement des
    categories (voir section 7) N'EST PAS un vrai ui.dialog()/ui.menu(),
    mais une ui.column basculee par .visible, STYLISEE pour ressembler a
    une boite de dialogue (classes Tailwind "fixed inset-0 z-50
    items-center justify-center bg-black/50" + une ui.card centree a
    l'interieur) sans en etre une techniquement - contourne le piege tout
    en gardant l'apparence attendue d'un dialogue modal. Ouvert/ferme
    depuis un bouton dans la VRAIE boite de dialogue Parametres (qui se
    ferme d'abord), pas de glisser-deposer entre les deux, un seul visible
    a la fois.

    A NE PLUS FAIRE : re-essayer de mettre make_sortable() dans un
    ui.dialog()/ui.menu() "parce que ca devrait marcher en theorie" (deja
    teste exhaustivement, toutes les pistes correctives usuelles echouent) -
    utiliser systematiquement le pattern "ui.column + .visible stylise en
    faux dialogue" pour tout futur besoin de glisser-deposer dans une
    boite modale.

8.13 PIEGE - une icone "voisine flex" (items-start) d'un bouton se
    retrouve EPINGLEE EN HAUT d'une box agrandie, pas centree sur le
    bouton (scene_button.py, corrige suite a une demande explicite :
    "pour les logos d'attention a cote des boutons, les centrer en
    hauteur par rapport au bouton").
    L'icone d'alerte de connexion (_build_connection_warning) etait
    construite comme un simple ELEMENT VOISIN du bouton dans une
    ui.row().classes("items-start gap-2") au niveau de _build() - correct
    tant que le bouton n'a RIEN en dessous, mais des que bib_on/target_on/
    intermediate_on/free_texts ajoutent des champs sous le bouton (le tout
    regroupe dans une "box" plus haute que le bouton seul), "items-start"
    aligne l'icone sur le HAUT DE LA BOX ENTIERE (correct visuellement,
    mais pas ce qu'on veut : l'icone doit rester au niveau du bouton,
    quelle que soit la hauteur du reste en dessous).
    SOLUTION (deja appliquee a l'icone de format indisponible, _build_
    format_warning, AVANT ce correctif - la meme technique a simplement
    ete etendue a l'icone de connexion) : construire l'icone A L'INTERIEUR
    du conteneur "relative" du bouton lui-meme (dans _build_button(), PAS
    dans _build()), positionnee en absolu ("absolute left-full top-1/2
    -translate-y-1/2") - le positionnement se calcule alors par rapport
    AU BOUTON SEUL (le plus proche ancetre "relative"), completement
    independant de ce qui est empile en dessous dans la box englobante.
    Les 2 icones (connexion + format) partagent maintenant un seul
    conteneur ui.row absolu commun (au lieu de 2 positionnements absolus
    separes) pour ne jamais se chevaucher quand les deux sont visibles en
    meme temps (ex: deconnecte ET mauvais format de course) - le conteneur
    porte le positionnement, les icones elles-memes ne gardent que leur
    style propre (couleur/taille/curseur).
    A NE PAS CONFONDRE avec _intermediate_warning_icon ("Selectionnez un
    intermediaire"), volontairement laissee au niveau de la combo box
    d'intermediaire (pas du bouton) : cet avertissement concerne
    specifiquement CE champ-la, pas le bouton dans son ensemble.

    SUITE IMMEDIATE (interface.py) : les icones ci-dessus etant en
    ABSOLU, elles debordent de leur propre cellule de grille CSS - avec
    l'ancien gap-4 uniforme (16px) entre colonnes, ce debordement (jusqu'a
    ~64px quand les 2 icones sont visibles en meme temps) chevauchait le
    bouton de la colonne suivante. D'ABORD corrige en elargissant le gap
    de grille ENTIER (gap-x-20 uniforme, 80px) - fonctionnait, mais
    ecartait TOUS les boutons meme ceux qui n'ont jamais d'icone.

    AFFINE ENSUITE (demande explicite : "si il n'y a pas d'icone d'erreur
    entre les boutons, faire en sorte que les boutons soient plus
    proches") : la grille est REVENUE a un gap-4 uniforme et modeste
    (16px), et c'est desormais CHAQUE BOUTON qui reserve (ou non) sa
    propre place via SceneButton._refresh_warning_spacing() - une marge
    "mr-20" (80px) ajoutee sur le conteneur du bouton (_button_container,
    memorise a la construction) UNIQUEMENT si au moins une des 2 icones
    (connexion/format) est actuellement visible, "mr-0" sinon. Appelee par
    les 2 fonctions qui changent une visibilite (_refresh_format_
    availability/_refresh_connection_warning), jamais l'inverse - chacune
    ne connait que son propre etat, cette fonction combine les deux.
    Consequence acceptee : `grid-auto-columns: max-content` dimensionne
    une colonne entiere sur son contenu le plus large, donc si UNE SEULE
    ligne de cette colonne a une icone, TOUTE la colonne s'elargit un peu
    (les autres lignes de la meme colonne ne "recuperent" pas cet espace)
    - limitation inherente a CSS Grid (impossible de varier le gap entre
    des paires de colonnes precises), acceptable et conforme a l'esprit de
    la demande (granularite par colonne, pas par ligne individuelle).
    Verifie visuellement ET par mesure DOM (protocole DevTools de Chrome) :
    27.6px entre 2 boutons sans aucune icone contre 123.6px entre 2
    boutons dont l'un affiche une icone de format indisponible - le ratio
    correspond exactement a la marge mr-20 ajoutee (aux arrondis du
    facteur BODY_ZOOM pres, voir section 6.2).

12bis. INTEGRATION STREAM DECK (Elgato Stream Deck XL)
--------------------------------------------------------
Materiel REELLEMENT teste tout au long du developpement (Stream Deck XL,
32 touches, 8 colonnes x 4 lignes, branche en USB) - toutes les
verifications ci-dessous ont ete faites sur le vrai peripherique, pas
seulement en logique pure.

V1 -> V2, CHANGEMENT DE PHILOSOPHIE (demande explicite de l'utilisateur,
apres une premiere version qui permettait de lancer des graphiques depuis
le Stream Deck) : "retirer les graphique du stream deck je ne veux pas
les lancer avec le stream deck". Le Stream Deck NE LANCE PLUS AUCUN
GRAPHIQUE - il sert desormais uniquement a :
    1) taper un dossard/une cible dans une boite de dialogue DEJA OUVERTE
       A LA SOURIS depuis l'interface web (_ask_bib/_ask_target) ;
    2) a defaut de boite ouverte, mettre a jour EN DIRECT le dossard/la
       cible du DERNIER graphique joue/pris DEPUIS L'INTERFACE WEB, qu'il
       soit en preview ou a l'antenne ;
    3) tourner les pages de ce meme dernier graphique, s'il est
       multipage_on (GOTO PAGE 1/PRECEDENTE/SUIVANTE) ;
    4) les actions globales du footer (ALL OUT/CLEAR PRW/TAKE PREVIEW/
       SWAP), identiques a celles de l'interface web (memes methodes de
       classe, aucune reimplementation).

PIEGES MAJEURS RENCONTRES ET CONTOURNES (voir streamdeck_hid.py et
streamdeck_controller.py pour le detail complet) :
    - Absence de hidapi.dll sur Windows : le package pip "streamdeck"
      (bibliotheque officielle) leve ProbeError des sa construction, MEME
      Stream Deck branche, car son seul transport reel charge un DLL natif
      qu'aucun package pip Windows ne fournit. SOLUTION : streamdeck_hid.py
      implemente un transport maison par-dessus le module `hid` (package
      pip "hidapi" de Trezor/cython-hidapi - DIFFERENT package pip du
      package "streamdeck" lui-meme), qui embarque hidapi dans son
      extension Cython compilee et fonctionne immediatement.
    - ui.notify() (et tout ce qui touche nicegui.context) hors d'une tache
      rattachee a un client NiceGUI leve RuntimeError - une touche
      physique n'est PAS un clic navigateur. SOLUTION : SceneButton.client
      (memorise a la construction) permet de re-entrer le contexte du
      client proprietaire via `with button.client:` avant tout appel
      touchant ce bouton, en plus d'un garde-fou try/except global
      (on_key_change) qui empeche de toute facon qu'une erreur d'affichage
      n'interrompe la lecture des touches physiques.
    - PIEGE DE TEST (pas un bug du logiciel, une lecon de methodologie) :
      ouvrir une boite de dialogue via asyncio.create_task() depuis un
      script de test EXTERIEUR a tout gestionnaire d'evenement NiceGUI
      reproduit artificiellement l'erreur "slot stack empty" ci-dessus,
      MEME quand le code de production n'a pas ce probleme (un vrai clic
      navigateur reste dans la meme tache du debut a la fin, y compris
      pendant l'attente `await dialog`). Verifie en cliquant reellement
      (protocole DevTools de Chrome, clic simule sur l'icone crayon d'un
      bouton reel) plutot qu'en simulant l'ouverture par du code Python
      artificiel - seule facon fiable de tester ce genre de flux.

13. COMPILATION EN EXECUTABLE (PyInstaller / auto-py-to-exe)
------------------------------------------------------------------

Objectif : pouvoir installer le logiciel sur un PC (hors environnement de
developpement Python) tout en continuant a l'utiliser normalement en mode
developpement (python main.py depuis le repo) - les deux doivent marcher
sans changement manuel entre les deux.

13.1 paths.py - fondation necessaire a la compilation
    Deux categories de fichiers, deux fonctions (voir aussi section 2) :
    - resource_path() : ressources EN LECTURE SEULE embarquees dans
      l'executable (assets/foxxprod_logo.png, templates.json "de base").
      En mode installe (FROZEN=True, attribut sys.frozen ajoute par le
      bootloader PyInstaller), pointe vers sys._MEIPASS - un dossier
      d'extraction TEMPORAIRE, different a chaque lancement, jamais a
      utiliser pour un fichier qu'on veut ecrire ou retrouver au
      prochain demarrage.
    - user_data_path() : fichiers UTILISATEUR modifiables par le
      logiciel lui-meme (config.json, templates.json une fois copie). En
      mode installe, %APPDATA%\BiathControlCenter (zone ecrivable SANS
      droits administrateur, contrairement au dossier d'installation
      habituel sous Program Files - point important, CasparCG tourne
      souvent sur un PC de regie sans compte admin permanent). En
      developpement, la racine du projet (FROZEN=False -> comportement
      strictement identique a avant l'introduction de paths.py).
    - ensure_user_file(filename) : au tout premier lancement en mode
      installe, si le fichier utilisateur n'existe pas encore, le copie
      depuis la ressource embarquee du meme nom (templates.json "de
      base" livre avec le logiciel) - sans jamais ecraser une copie
      utilisateur deja modifiee. Utilise pour templates.json (contenu
      significatif a preserver), PAS pour config.json (dont l'absence
      est deja geree nativement par app_config.load_config() via
      DEFAULT_CONFIG, pas besoin de "graine").

    interface.py (LOGO_PATH), buttons_config.py (BUTTONS_CONFIG_PATH) et
    app_config.py (CONFIG_PATH) passent tous les trois par paths.py -
    aucun ne construit plus son propre chemin via Path(__file__)
    directement (verifie : seul paths.py y fait encore reference).

    BUG REEL RENCONTRE ET CORRIGE - "pourquoi quand je compile le
    logiciel je n'ai pas tous les boutons qui apparaissent ?" :
    consequence DIRECTE du "sans jamais ecraser" d'ensure_user_file()
    ci-dessus, VOULU pour proteger les options de free_text ajoutees en
    direct par l'operateur, mais qui a un effet de bord non voulu : une
    fois le tout premier lancement passe, la copie utilisateur de
    templates.json reste figee pour toujours, MEME apres avoir recompile
    une version plus recente du logiciel avec de nouveaux boutons ajoutes
    au templates.json source - la copie deployee (%APPDATA%) ne les
    voit jamais. Corrige dans buttons_config.py (PAS dans ensure_user_file()
    lui-meme, qui reste generique - ce fichier connait la STRUCTURE de
    templates.json, paths.py non) : merge_bundled_templates(bundled, user)
    complete la copie utilisateur avec les entrees du templates.json
    EMBARQUE dans l'executable qui n'y sont pas deja, identifiees de
    facon stable par _entry_identity() - (template, layer, cg_layer) pour
    un vrai bouton (ce qui est REELLEMENT envoye a CasparCG, un simple
    "label" ne suffit pas car 2 boutons differents peuvent le partager),
    (section, column) pour les entrees "_column_title"/"_restrict_controls".
    PUREMENT ADDITIF : n'ecrase JAMAIS une entree deja presente cote
    utilisateur (ses eventuelles options de free_text ajoutees en direct
    restent intactes), et ne RETIRE JAMAIS une entree presente cote
    utilisateur mais absente cote embarque (un bouton personnalise ajoute
    par l'operateur lui-meme, ou un bouton retire dans une version plus
    recente, ne doit jamais disparaitre du jour au lendemain).
    _merge_bundled_templates_on_startup() execute cette fusion UNE SEULE
    FOIS a l'import du module (donc au tout premier chargement de page),
    UNIQUEMENT si FROZEN (en developpement, resource_path() et
    user_data_path() pointent vers le MEME fichier, une fusion n'y aurait
    aucun sens) - jamais fatal, un templates.json embarque manquant ou
    invalide ne bloque jamais le demarrage (try/except large, le logiciel
    continue simplement avec la copie utilisateur telle quelle).
    Teste de bout en bout (fichiers de scratch, resource_path/
    user_data_path/FROZEN monkeypatches - jamais le vrai templates.json) :
    un bouton nouveau cote "bundled" est bien ajoute cote "user" ; un
    bouton deja present AVEC une personnalisation (option de free_text)
    reste inchange ; un bouton purement personnalise cote "user" (absent
    du "bundled") survit ; un deuxieme appel sans rien de nouveau est un
    no-op strict (fichier byte-a-byte identique, aucune reecriture
    inutile).

13.2 BiathControlCenter.spec - configuration PyInstaller
    A compiler avec `pyinstaller BiathControlCenter.spec` (plus fiable et
    reproductible que de reconfigurer manuellement l'interface graphique
    auto-py-to-exe a chaque fois - auto-py-to-exe N'EST QU'UNE interface
    graphique par-dessus PyInstaller, elle ne charge pas directement un
    fichier .spec existant). Points cles :
    - Mode "onedir" (COLLECT, pas juste EXE onefile) : demarrage plus
      rapide qu'un onefile qui doit se re-extraire dans un dossier
      temporaire a CHAQUE lancement - preferable pour un usage en direct
      pendant une diffusion, ou la reactivite au demarrage compte.
    - collect_all("nicegui") (PyInstaller.utils.hooks) : NiceGUI embarque
      ses propres ressources statiques (JS/CSS/polices/favicon) qui
      doivent etre incluses telles quelles, sinon l'interface ne se
      charge pas une fois compile - piege documente par NiceGUI elle-meme
      pour tout packaging PyInstaller/Nuitka, pas verifie en pratique ici
      (pas d'environnement de build disponible pour tester la compilation
      elle-meme) mais applique par prudence.
    - datas inclut assets/ (logo) et templates.json (catalogue "de base",
      voir 13.1) - PAS config.json (jamais embarque, uniquement cree/lu
      dans %APPDATA% en mode installe).
    - console=True (choix delibere, PAS le defaut "propre" console=False
      d'une appli Windows) : main.py affiche l'etat de connexion CasparCG/
      WebSocket via print() au demarrage, et des erreurs peuvent remonter
      sur stdout/stderr en cours d'usage (ex: le ConnectionResetError
      deja rencontre en developpement, section historique du projet).
      PIEGE PyInstaller CONNU : en mode "windowed" (console=False),
      sys.stdout/stderr valent None dans un executable sans console - un
      print() ou un traceback non catche peut alors LEVER UNE EXCEPTION
      au lieu de simplement s'afficher, ce qui est pire qu'une fenetre de
      console en plus. A ne repasser en console=False que si le logiciel
      est juge stable ET qu'aucun print()/traceback resultant n'est plus
      possible.
    - main.py utilise deja reload=False dans ui.run() (piege 8.6,
      necessaire pour un executable compile - NiceGUI reload=True repose
      sur un mecanisme de re-spawn de process qui ne marche pas une fois
      frozen). Deja correct avant ce travail de compilation, rien a
      changer ici.

13.3 requirements.txt
    Dependances RUNTIME seulement (nicegui, websockets), epinglees aux
    versions utilisees en developpement (nicegui 3.16.0, websockets
    15.0.1 au moment ou ce travail a ete fait). PyInstaller et
    auto-py-to-exe sont des OUTILS DE BUILD (deja installes separement
    dans l'environnement de developpement au moment de ce travail :
    PyInstaller 6.11.1, auto-py-to-exe 2.45.0), pas des dependances de
    l'application elle-meme - volontairement absents de requirements.txt.
    Ajoute avec l'integration Stream Deck (voir section 12bis) : streamdeck
    (python-elgato-streamdeck, bibliotheque officielle - fournit les
    classes StreamDeckXL/PILHelper/etc., mais PAS le transport HID
    fonctionnel sous Windows, voir streamdeck_hid.py), hidapi (package pip
    de Trezor/cython-hidapi, module `hid` - fournit le VRAI acces materiel
    sous Windows, contrairement a ce que son nom pourrait suggerer pour le
    package "streamdeck" seul), Pillow (dessin des icones, streamdeck_
    icons.py). A verifier avant compilation PyInstaller (section 13.4) :
    ces 3 packages (extensions compilees pour hidapi/Pillow) doivent etre
    correctement embarques - pas seulement testes en environnement de
    developpement.

13.4 Non verifie / a tester
    Aucune compilation reelle n'a ete effectuee pendant ce travail (pas
    d'environnement de build/execution disponible pour lancer
    `pyinstaller BiathControlCenter.spec` et verifier l'executable
    resultant). A tester avant un usage en production :
    - Que l'executable demarre bien et que l'UI NiceGUI se charge
      (risque principal : ressources NiceGUI manquantes malgre
      collect_all, cas documente comme frequent pour ce framework).
    - Que templates.json est bien copie dans %APPDATA%\BiathControlCenter
      au premier lancement, et que les ecritures ulterieures (ajout
      d'option de free_text, futures fonctionnalites) persistent bien
      la-bas et pas dans le dossier d'installation.
    - Que config.json se cree correctement au premier lancement dans le
      meme dossier %APPDATA%.
    - Icone : icon.ico (racine du projet, PAS encore ajoute au repo au
      moment ou ceci est ecrit) utilise a DEUX endroits distincts, a ne
      pas confondre : icon="icon.ico" dans EXE() (icone du fichier .exe,
      gravee a la compilation) ET dans `datas` + main.py
      (resource_path("icon.ico"), passe a ui.run(favicon=...) - copie
      embarquee lue A L'EXECUTION pour l'onglet du navigateur, PyInstaller
      ne rend pas l'icone .exe elle-meme accessible comme fichier une
      fois compilee). favicon= est optionnel cote code (retombe sur None
      si icon.ico est absent, ne bloque pas le demarrage), mais icon.ico
      DOIT exister pour que la compilation reussisse (les deux endroits
      y font reference sans verification d'existence a la compilation).
      PIEGE COURANT (pas un bug de compilation) : l'icone du .exe
      n'apparaissant pas dans l'Explorateur Windows apres compilation est
      generalement le CACHE D'ICONES Windows, pas un probleme reel - voir
      compiler.txt pour les solutions (renommer le fichier, redemarrer
      l'Explorateur, etc.).
