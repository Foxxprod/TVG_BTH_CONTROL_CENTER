BIATH CONTROL CENTER - CONTEXTE DU PROJET
============================================

Ce fichier a ete entierement reecrit le 25/08/2026 pour refleter l'etat reel
du projet apres une premiere phase de developpement. Il remplace la version
initiale (qui decrivait un projet vide, au stade de conception).


1. OBJECTIF DU PROJET
----------------------

Biath Control Center est un logiciel de controle pour piloter les habillages
televisuels pendant une course de biathlon.

Le logiciel permet a un operateur de suivre les donnees de la course en
temps reel et de declencher les habillages graphiques dans CasparCG de
maniere rapide, fiable et comprehensible pendant une diffusion en direct.

Un logiciel distinct (deja existant, non modifie par ce projet) genere et
diffuse les donnees de la course de biathlon via WebSocket. Biath Control
Center consomme ces donnees et pilote CasparCG ; il ne remplace pas le
logiciel de donnees.


2. ETAT ACTUEL DU REPO
----------------------

Fichiers principaux :

- main.py
    Point d'entree. Charge config.json (app_config.load_config), cree les
    instances globales `caspar` (CasparCG) et `data` (BiathDataWebsocket)
    a partir de ce config, declare la page NiceGUI ("/"), appelle
    build_header(caspar, data, config), build_body() et build_footer(),
    connecte caspar/data au demarrage du serveur (@app.on_startup), lance
    ui.run().

- app_config.py
    load_config()/save_config(config) : lit/ecrit config.json (theme
    clair/sombre, titre du logiciel, ip/port du serveur de donnees,
    ip/port CasparCG, numeros de channel preview/programme). Fichier
    absent ou incomplet -> complete avec DEFAULT_CONFIG. config.json N'EST
    PAS commite (voir .gitignore) : c'est un reglage d'instance/machine,
    contrairement a templates.json (catalogue de graphiques, commite). Le
    dict `config` charge dans main.py est passe par reference a
    build_header, qui le modifie et le sauvegarde depuis la boite de
    dialogue Parametres (voir 6.1) - source de verite unique partagee.

- casparcg.py
    Couche de communication AMCP avec CasparCG. Implementation maison
    (pas de librairie tierce) : ouverture de socket TCP brut, envoi de
    commandes texte, parsing des reponses selon le protocole AMCP.
    Contient la classe CasparCG et le dataclass AMCPResponse.

- biathdata_ws.py
    Couche de communication WebSocket avec le logiciel de donnees
    biathlon. Utilise la librairie tierce `websockets` (contrairement a
    casparcg.py, le protocole WebSocket est trop complexe/risque a
    reimplementer a la main). Contient la classe BiathDataWebsocket.

- interface.py
    Construction de l'interface NiceGUI : barre d'outils du haut
    (build_header) et corps de page (build_body). Ne contient aucune
    logique bas niveau AMCP/WebSocket, uniquement de l'affichage et des
    appels aux methodes publiques de CasparCG/BiathDataWebsocket.
    build_body divise le corps en 3 conteneurs empiles verticalement
    (PRE RACE / RACE / POST RACE, voir SECTIONS), chacun organise en une
    VRAIE grille CSS (fonction interne add_button(section, row, column,
    **kwargs_scene_button)) : chaque case est un ui.column positionne
    explicitement via grid-row/grid-column (style CSS), pas des ui.row
    flex independantes par ligne - sinon "colonne N" ne s'alignerait pas
    entre les lignes (bug reel rencontre et corrige : avec des lignes flex
    independantes, la colonne N d'une ligne n'est que sa N-ieme case a
    elle, sans lien avec la colonne N d'une autre ligne qui a moins
    d'entrees). Les 3 conteneurs ne se partagent PAS la hauteur a parts
    egales : PRE RACE et POST RACE se reduisent a leur hauteur de contenu
    (comportement flex par defaut, flex-grow 0), RACE absorbe tout le
    reste de la hauteur disponible (flex-1) - ex: POST RACE avec 2
    boutons reste compact, RACE s'etend d'autant plus. Choix explicite de
    l'utilisateur, RACE cible en dur (pas de logique dynamique "la section
    avec le plus de contenu grandit" - non faisable en CSS pur sans mesurer
    le contenu en JS). Les boutons a creer sont lus depuis templates.json
    via buttons_config.load_button_configs().

- buttons_config.py
    load_raw_configs() : lit templates.json TEL QUEL (liste brute, sans
    filtrage). load_button_configs(raw=None)/load_column_titles(raw=None) :
    filtrent+valident (boutons vs titres de colonne "_column_title", en
    ignorant "_example") ; si `raw` est fourni (voir build_body), evite une
    relecture independante du fichier - important pour que les dicts
    obtenus soient les MEMES objets que ceux geres ailleurs (persistance,
    voir plus bas). save_button_configs(raw) : reecrit integralement le
    fichier. Renvoie [] avec un message si le fichier est absent. Leve une
    ValueError si le JSON n'est pas une liste ou si un champ obligatoire
    manque sur une definition (section/label/template/layer pour un
    bouton, section/column/title pour un titre de colonne).

- templates.json
    Catalogue des boutons de l'interface, un objet JSON par SceneButton.
    C'est le point d'entree normal pour ajouter/modifier/retirer un
    graphique : plus besoin de toucher au code Python, y compris une fois
    le logiciel compile/livre. PEUT AUSSI ETRE REECRIT PAR LE LOGICIEL
    LUI-MEME (pas seulement lu) : ajouter une option a un free_text en
    direct depuis l'interface (icone "+", voir section 7) persiste ce
    changement ici via buttons_config.save_button_configs(). Commence par

- scene_button.py
    Classe SceneButton : brique reutilisable representant un graphique
    CasparCG pilotable (play preview/programme, take, stop, pages
    multiples, saisie de dossard, saisie de valeur target, envoi
    automatique de l'ip du websocket). C'est le mecanisme prevu pour
    ajouter facilement de nouveaux graphiques a l'interface (instancie
    desormais depuis templates.json plutot qu'a la main dans interface.py).
    Maintient un registre de toutes les instances vivantes
    (SceneButton._instances) ; SceneButton.reset_all() remet tous les

- biathdata_reference.txt
    Documentation de reference de tous les champs disponibles dans un

    partir d'un exemple reel fourni par l'utilisateur.

- assets/foxxprod_logo.png
    Logo affiche dans la barre d'outils.

- biath_data.py
    Fichier historique vide, non utilise. La logique WebSocket vit en
    realite dans biathdata_ws.py (renomme/reoriente en cours de route).

- paths.py
    resource_path()/user_data_path()/ensure_user_file() : centralisent la

- requirements.txt
    Dependances RUNTIME (nicegui, websockets), epinglees aux versions

- BiathControlCenter.spec
    Specification PyInstaller pour compiler le logiciel en executable

Version de Python utilisee en developpement : 3.13 (Python313, observe

3. TECHNOLOGIES CONFIRMEES
---------------------------

- Python (3.13 en dev).
- NiceGUI pour l'interface operateur (confirme et utilise).
- asyncio pour tout le code reseau et les taches de fond (reconnexion,
  ping, retrait automatique de graphiques...).
- Client AMCP : implementation interne maison sur socket TCP brut (pas de
  librairie tierce). Choix assume : protocole texte simple, controle total
  du comportement (timeouts, reconnexion), pas de dependance externe a
  maintenir pour un usage broadcast en direct.
- Client WebSocket : librairie tierce `websockets` (pip install websockets).
  Choix assume different d'AMCP : le protocole WebSocket (handshake HTTP
  Upgrade, framing, masking, ping/pong de controle) est trop complexe et
  risque a reimplementer correctement a la main.
- Aucune API web publique construite par-dessus NiceGUI : NiceGUI gere la
  communication navigateur <-> serveur en interne.


4. CASPARCG.PY - DETAIL DE L'IMPLEMENTATION
---------------------------------------------

4.1 AMCPResponse (dataclass)
    - code: int, message: str, data: list[str]
    - is_info      -> 100 <= code < 200
    - is_success    -> 200 <= code < 400
    - is_error      -> code == 0 (erreur locale/reseau) ou code >= 400

4.2 Classe CasparCG - constructeur
    CasparCG(ip, port, channel_programm, channel_preview, timeout=5.0,
             reconnect=True, reconnect_delay=5.0)
    channel_programm/channel_preview DOIVENT correspondre aux channels
    reellement definis dans le casparcg.config du serveur CasparCG cible
    (voir section 7, un mismatch a deja cause une erreur "Invalid channel
    specified").

    Etat interne : reader/writer asyncio, connected (bool), _lock
    (asyncio.Lock, serialise les commandes), _preview (dict, dernier
    template/data/cg_layer/play_on_load envoye en preview), _ping_interval
    (5.0s), _ping_task, _remove_delay (5.0s), _pending_removals (dict
    (address, cg_layer) -> Task, pour l'auto-remove differe apres stop()).

4.3 Fonctions internes/techniques (prefixees _, ou non destinees a un
    usage direct depuis le reste du logiciel) :
    - ping() : envoie "PING\r\n", compare la reponse brute a "PONG" (PING
      est un cas special du protocole AMCP, il ne suit PAS le format
      "XXX message" standard), met a jour self.connected.
    - _ping_loop() : boucle unique de fond. Si connecte -> attend
      ping_interval puis ping(). Si deconnecte et self.reconnect ->
      attend reconnect_delay puis _reconnect(). Sinon, arrete la boucle.
      Sequentiel : jamais deux tentatives de reconnexion en parallele.
    - _reconnect() : ferme l'ancienne connexion si presente, en ouvre une
      nouvelle, appelle ping().
    - send_command(command) : envoie une commande AMCP brute, retourne un
      AMCPResponse. Retourne code=0 "Not connected" si non connecte.
    - _read_response() : parse une reponse (code + message), et pour les
      reponses multi-lignes (code 200), continue de lire jusqu'a une
      ligne vide terminale.
    - _channel_number(channel) : "prw" -> channel_preview, "pgm" ->
      channel_programm, sinon ValueError.
    - format_address(channel, layer=None) : "prw" -> toujours
      "{channel_preview}-1" (layer ignore, force a 1). "pgm" -> exige un
      layer explicite (ValueError sinon).
    - _escape_amcp_string(value) / _escape_xml(value) : echappement pour
      parametres AMCP entre guillemets et pour attributs XML.
    - format_template_data(data: dict) : convertit un dict cle/valeur en
      XML CasparCG classique :
        <templateData><componentData id="CLE"><data id="text"
        value="VALEUR"/></componentData>...</templateData>
      CONFIRME avec un exemple XML reel fourni par l'utilisateur. Les
      cles du dict correspondent aux VRAIS noms de champs du template
      (pas de convention generique f0/f1) : chaque template a ses propres
      noms de champs.
    - _schedule_remove(...) / _delayed_remove(...) : programment un
      CG REMOVE automatique remove_delay secondes apres un stop(), annule
      si un nouveau graphique est charge sur le meme (channel-layer,
      cg_layer) avant l'echeance.

4.4 Fonctions publiques (a utiliser depuis le reste du logiciel) :
    - connect() : ouvre la connexion TCP, verifie via PING/PONG, DEMARRE
      TOUJOURS la boucle de fond _ping_loop meme si cette premiere
      tentative echoue (pour que CasparCG indisponible au demarrage soit
      retente automatiquement au lieu d'abandonner). Retourne None ou un
      message d'erreur.
    - disconnect() : envoie BYE (sur, car on est toujours en connexion
      distante/reseau, jamais en console locale CasparCG - BYE ne fait
      donc que deconnecter, il n'eteint pas le serveur) puis ferme le
      socket. Annule _ping_task et toutes les taches _pending_removals.
    - play_template(channel, template, data=None, layer=None, cg_layer=1,
      play_on_load=True) : construit et envoie CG ADD. Si succes, annule
      tout auto-remove programme pour ce (channel-layer, cg_layer), et si
      channel=="prw", memorise l'etat dans self._preview.
    - update_template(channel, data, layer=None, cg_layer=1) : CG UPDATE.
      Met a jour self._preview["data"] si c'est la preview qui est mise a
      jour avec succes.
    - remove_template(channel, layer=None, cg_layer=1) : CG REMOVE
      (retire completement le producer, contrairement a stop()).
    - stop(channel, layer=None, cg_layer=1) : CG STOP, puis programme un
      CG REMOVE automatique 5s plus tard (annulable, voir 4.3).
    - clear(channel, layer=None) : CLEAR generique (retire N'IMPORTE quel
      producer, video/image/graphique, pas seulement les templates CG).
      Si layer est omis, clear tout le channel. Reinitialise self._preview
      si c'est la preview qui est cleared avec succes.
    - play_prw_to_pgm(layer) : le "Take". Rejoue (recopie la commande et
      les donnees, choix assume plutot que cloner une composition deja
      preparee) le template/data actuellement memorise en preview vers le
      programme au layer donne, puis stoppe la preview. Retourne une
      erreur "Nothing in preview to take" si rien n'a ete joue en preview
      au prealable (ou si le dernier play a echoue).
    - emergency_all_out() : clear("prw") + clear("pgm"), retourne les deux
      AMCPResponse. Vide integralement les deux channels (tout producer,
      y compris les graphiques).
    - change_connection(ip=None, port=None, channel_preview=None,
      channel_programm=None) : disconnect() puis met a jour les attributs
      fournis (les autres restent inchanges) puis connect(). Retourne None
      ou un message d'erreur (meme contrat que connect()). Utilise par la
      boite de dialogue Parametres (voir 6.1) pour appliquer un changement
      d'IP/port/channel EN DIRECT, sans redemarrer le logiciel. Reconnecte
      toujours (meme un simple changement de channel, qui ne necessite pas
      forcement une nouvelle connexion TCP) - choix assume par simplicite.

4.5 Rappels de protocole AMCP (source : wiki AMCP CasparCG, la doc note
    elle-meme qu'elle peut etre datee, a re-verifier avec
    casparcg.com/docs/wiki si besoin) :
    - Reponses : code 3 chiffres + message. 100-101 info. 200-202 succes
      (200 = multi-lignes terminees par une ligne vide, 201/202 = une
      seule ligne). 400-404 erreur client. 500-503 erreur serveur.
    - Encodage UTF-8, terminaison de commande "\r\n".
    - Parametres avec espaces entre guillemets, echappement \" et \\.
    - Adressage channel-layer : "1" (tout le channel), "1-1", "1-10",
      "-0" (layer par defaut).
    - CG ADD [layer] "template" [play-on-load 0/1] {"data"}
    - CG UPDATE [cg_layer] "data"
    - CG REMOVE [cg_layer]
    - CG STOP [cg_layer]
    - CG CLEAR (sans cg_layer, ne retire que les templates CG)
    - CLEAR (generique, retire tout producer)
    - BYE deconnecte a distance / eteint le serveur en local.


5. BIATHDATA_WS.PY - DETAIL DE L'IMPLEMENTATION
--------------------------------------------------

5.1 Classe BiathDataWebsocket - constructeur
    BiathDataWebsocket(ip, port, path="/", timeout=5.0, reconnect=True,
                        reconnect_delay=5.0)
    url (property) = f"ws://{ip}:{port}{path}"

    Etat expose : latest_data (dict JSON brut du dernier message de
    chronometrage complet), config (SimpleNamespace), event_infos
    (SimpleNamespace), timing_data (dict[str, SimpleNamespace] cle =
    dossard), connected (bool).

5.2 Fonctions publiques :
    - connect() : ouvre la connexion websocket, DEMARRE TOUJOURS la
      boucle de fond _receive_loop meme si la premiere tentative echoue
      (meme logique que CasparCG.connect(), pour retenter automatiquement
      un serveur de donnees indisponible au demarrage).
    - disconnect() : annule _receive_task, ferme la connexion.
    - change_ip(ip, port=None) : met a jour l'adresse ; si deja connecte,
      se deconnecte puis se reconnecte a la nouvelle adresse.

5.3 Fonctions internes :
    - _receive_loop() : boucle unique de fond, meme principe que
      _ping_loop de CasparCG. Si connecte, consomme les messages
      (async for) jusqu'a perte de connexion. Si deconnecte et
      self.reconnect, attend reconnect_delay puis _reconnect(). Jamais
      deux tentatives en parallele.
    - _reconnect() : ferme l'ancien websocket si present, en ouvre un
      nouveau.
    - _handle_message(raw_message) :
        1. json.loads(raw_message). PARTICULARITE DECOUVERTE EN TEST : le
           serveur encode parfois le JSON DEUX FOIS (le message recu est
           une string JSON qui contient elle-meme du JSON en texte
           echappe). Le code detecte ce cas (resultat = str) et refait un
           second json.loads.
        2. Si le dict resultant contient les cles "config", "event_infos"
           ET "timing_data", c'est un snapshot COMPLET de chronometrage
           (pas un delta) : latest_data, config, event_infos et
           timing_data sont remplaces integralement.
        3. D'AUTRES TYPES DE MESSAGES passent sur le meme WebSocket
           (confirme par l'utilisateur) mais ne sont PAS encore geres :
           ils sont ignores silencieusement pour l'instant. A implementer
           plus tard.
    - _sanitize_key(key) : remplace tout caractere non valide pour un
      attribut Python (ex: espace) par "_". Necessaire car le JSON reel
      contient au moins une cle avec espace : "EVENT NAME" ->
      accessible via event_infos.EVENT_NAME.
    - _to_namespace(data: dict) : convertit un dict en SimpleNamespace en
      assainissant les cles.

5.4 Format reel des messages WebSocket : voir biathdata_reference.txt
    pour le detail complet champ par champ. Points cles :
    - Chaque message de chronometrage contient un etat COMPLET (pas un
      delta), a remplacer integralement a chaque reception.
    - timing_data est indexe par dossard (string), ex: "1", "2"...
    - Les noms de champs (C_NUM, C_LAST_NAME, C_TIME, C_STATUS,
      C_INTERSHOOT1..8, C_INTERSLOPE1..12, etc.) sont documentes dans
      biathdata_reference.txt avec leur variable d'acces exacte.
    - C_START et les C_INTER... sont TRES PROBABLEMENT en millisecondes
      depuis minuit (deduit, pas confirme par le fournisseur).
    - VOLADBNUMBER et C_SHOOTING_RACE_NUMBER : signification non
      identifiee avec certitude.


6. INTERFACE.PY - DETAIL DE L'IMPLEMENTATION
-----------------------------------------------

6.1 build_header(caspar, data, config)
    Barre d'outils fixe en haut de page (ui.header), style sombre
    (bg-slate-900), avec marge (m-3) et coins arrondis sur les 4 cotes
    (rounded-2xl, overflow-hidden pour que les elements colles respectent
    l'arrondi).

    Contenu, de gauche a droite :
    - Logo (assets/foxxprod_logo.png, dimensions fixes h-10 w-16).
    - Panneau blanc "flush" (pleine hauteur du header, sans bordure ni
      arrondi individuel) avec le titre du logiciel (software_title_label,
      texte initial config["software_title"], modifiable en direct depuis
      Parametres - plus jamais "BIATHLON - CONTROL CENTER" fige en dur).
    - Titre de l'epreuve (data.event_infos.TITLE) et nom de la course
      (data.event_infos.EVENT_NAME, en gras), meme taille de police,
      separes par un tiret.
    - Bouton icone "settings" (rond, contour slate) : ouvre settings_dialog
      (voir plus bas).
    - Bouton "EMERGENCY ALL OUT" (contour rouge, fond rouge legerement
      transparent bg-red-600/20, icone warning) : appelle
      caspar.emergency_all_out() et notifie le resultat.
    - Case de statut CASPARCG et case de statut WS DATA (fonction
      _build_status_box) : chaque case fait moitie haut (titre) / moitie
      bas (statut colore, fond legerement transparent, clignote lentement
      - animate-pulse - si deconnecte), largeur fixe identique (w-32),
      collees entre elles (bordure gauche fine, pas de marge).
    - Cases HEURE et TEMPS COURSE (fonction _build_clock_box) : fond
      blanc, cote a cote, heure actuelle et decompte/chrono de course
      (calcule depuis event_infos.STARTHOUR par format_race_clock).

    Tout se rafraichit chaque seconde via ui.timer(1.0, update_header).
    Le fond de la PAGE (pas du header) est regle par apply_body_background()
    (bg-slate-50 clair / bg-slate-900 sombre selon config["dark_mode"]).
    build_header() neutralise aussi le padding HORIZONTAL par defaut de
    NiceGUI autour du contenu de page (ui.query(".nicegui-content")
    .style("padding-left: 0; padding-right: 0;"), PAS le padding-top/
    bottom - voir piege 8.9) pour que build_body/build_footer restent
    alignes avec le header.

    Boite de dialogue Parametres (settings_dialog, construite UNE FOIS,
    pas a chaque ouverture - contrairement aux boites ephemeres de
    scene_button.py, car le header est present en permanence) :
    - Mode sombre (ui.switch) : pilote ui.dark_mode() (composants Quasar
      natifs : dialogues, champs...), apply_body_background() (fond de
      page) ET SceneButton.set_dark_mode() (cartes de section PRE RACE/
      RACE/POST RACE + chaque SceneButton : box, bouton, labels bib/
      target - voir 7). Le header/footer restent sombres en permanence
      dans les deux modes (deja bg-slate-900 fixe), non concernes.
      SceneButton sert de point de coordination central pour le theme
      (comme il l'est deja pour _active_preview/_active_pgm) :
      set_dark_mode() rafraichit direct tous les SceneButton deja
      construits ET previent les abonnes externes via
      on_dark_mode_change() (utilise par build_body pour ses cartes de
      section, qui ne sont pas des SceneButton mais doivent suivre le
      meme theme - evite de dupliquer un etat sombre/clair separe dans
      interface.py). Restent NON adaptes au theme (portee volontairement
      limitee) : icones bib/target/connexion (gris moyen, lisible dans
      les deux modes en pratique), panneaux blancs internes du header
      (titre logiciel, HEURE/TMPS COURSE) - accents "papier" volontaires
      sur le header deja sombre en permanence, pas lies au toggle.
    - Titre du logiciel (ui.input).
    - IP/port du serveur de donnees WebSocket, IP/port CasparCG, numero de
      channel preview et programme (ui.input/ui.number).
    on_settings_save() : met a jour le dict `config` (valeur vide/nulle
    d'un champ -> garde l'ancienne valeur plutot que d'ecraser, protection
    minimale), appelle app_config.save_config(config) pour persister dans
    config.json, PUIS applique tout immediatement (dark_mode.set_value,
    apply_body_background, software_title_label.text) et reconnecte en
    direct data.change_ip(...) et caspar.change_connection(...) - sans
    redemarrer le logiciel, exactement l'exigence formulee par
    l'utilisateur pour cette fonctionnalite. Notifie une erreur de
    connexion si change_ip/change_connection en renvoie une (les
    parametres restent quand meme enregistres - la reconnexion se fera
    seule via les boucles de fond _ping_loop/_receive_loop habituelles).

6.3 build_footer(caspar, data)
    Pied de page (ui.footer), meme style que le header (bg-slate-900,

      actuellement au programme. Ne touche pas a la preview.
      DIFFERENT de "EMERGENCY ALL OUT" (header) qui fait un CLEAR
      immediat des deux channels entiers (tout producer, pas seulement
      les boutons CG, sans animation de sortie).
    - "CLEAR PRW" (contour jaune) : caspar.clear("prw", layer=1) puis
      SceneButton.reset_preview_button() pour resynchroniser l'affichage
      du bouton qui occupait la preview.

6.4 Points d'architecture NiceGUI importants (voir aussi section 8) :
    - build_header/build_body/build_footer sont appeles depuis une
      fonction decoree @ui.page("/") dans main.py, PAS au niveau module.
      C'est une correction critique (voir section 8.5).


7. SCENE_BUTTON.PY - DETAIL DE L'IMPLEMENTATION
----------------------------------------------------

Classe SceneButton : represente un graphique CasparCG pilotable. Concu
comme LE moyen d'ajouter facilement un nouveau graphique a l'interface et
de controler les donnees qui lui sont envoyees.

Constructeur :
    SceneButton(caspar, data, label, template, layer, cg_layer=1,
                extra_data=None,
                send_ip=False, field_ip="ip",
                bib_on=False, field_bib="bib",
                multipage_on=False, field_page="page",
                reset_page_on_play=False,
                target_on=False, field_target="target",
                free_texts=None)

    Les noms de champs (field_ip, field_bib, field_page, field_target)
    sont CONFIGURABLES par bouton (chaque template CasparCG peut avoir
    ses propres noms de champs), SAUF que la VALEUR du champ ip est
    toujours automatiquement celle du serveur websocket (data.ip), non
    saisie par l'operateur. send_ip n'envoie que l'IP, pas le port.

Comportement au clic (corps du bouton, forme pilule rounded-full comme
le bouton EMERGENCY) :
    - etat "idle"      -> clic = play_template vers preview
    - etat "preview"   -> clic = play_prw_to_pgm (Take vers programme)
    - etat "programme" -> clic sans effet (protection contre un replay
      accidentel d'un graphique en direct ; seul le survol "OUT" peut
      l'arreter)

Survol : un petit rectangle apparait directement au-dessus du bouton
(colle, sans espace mort, pour rester cliquable en y deplacant la
souris), fond noir/gris fonce (bg-slate-800) :
    - "IN"  (idle/preview) -> clic = envoi DIRECT au programme (sans
      passer par la preview)
    - "OUT" (programme)    -> clic = stop() du graphique

Multipage (multipage_on=True) : fleches gauche/droite integrees dans le
corps du bouton (chevron_left/chevron_right). Le compteur "page"
s'incremente/decremente SANS limite haute (plancher a 1, decision
utilisateur : "compteur infini"). Si le graphique est deja affiche, le
changement de page pousse immediatement un update_template.

Selection de dossard (bib_on=True) : boite de dialogue (_ask_bib) avec un
champ de recherche texte (autofocus fiabilise par .props("autofocus") + un
ui.timer de secours qui force le focus), qui filtre en direct la liste
des athletes (data.timing_data, tri par dossard croissant, recherche sur
"dossard - NOM prenom") dans une variable locale `filtered` recalculee a
chaque frappe. Navigation : fleches haut/bas (keydown.up/down.prevent)
deplacent un index de surlignage `selected_index[0]` dans `filtered`
(liste circulaire, retour au debut/fin), Entree ou le bouton "Valider"
confirment l'athlete actuellement surligne (`confirm_selected`). Chaque
ligne de la liste reste aussi cliquable individuellement (selection
directe, liste scrollable). Si le champ de recherche est vide,
`selected_index[0]` demarre a -1 : RIEN n'est surligne par defaut (il
faut taper, cliquer, ou utiliser les fleches pour commencer a naviguer
dans la liste complete).

Le dossard est capture une seule fois au premier play, puis reutilise tel
quel pour le Take (comme les autres donnees memorisees dans
CasparCG._preview). Une fois selectionne, l'athlete choisi est affiche
SOUS le bouton (dans la meme box bordee que les eventuels free_texts, voir
SceneButton._build : la box n'apparait que si bib_on ou free_texts est
actif) avec une icone crayon a cote (_build_bib_display) qui rouvre
_ask_bib a tout moment, pas seulement au premier play
(_on_change_bib_click) : si le graphique est deja affiche (preview ou
programme), le nouveau dossard est pousse immediatement via
update_template, sinon juste memorise pour le prochain play.

Saisie de target (target_on=True) : apres le PREMIER play reussi
(preview ou direct-pgm via "IN" ; pas re-demande au moment du Take),
boite de dialogue avec un champ numerique borne entre 1 et 30. La valeur
saisie est envoyee via update_template.

Champs de saisie libre (free_texts=[{...}, ...]) : zone(s) de saisie
affichees SOUS le bouton (pas dans une boite de dialogue, contrairement a
bib_on/target_on), une par entree de la liste. Chaque entree : "field"
(cle envoyee au template, obligatoire), "label" (affiche sur le champ,
defaut = field), "options" (liste de strings, optionnelle).
    - Sans "options" : une seule ligne, simple ui.input texte libre.
    - Avec "options" : DEUX lignes - une combo box (ui.select, limite aux
      options) ET un ui.input texte libre juste en dessous (label "Texte
      libre"), mutuellement exclusifs : choisir une valeur dans la combo
      box vide le texte libre (input_widget.set_value(None)) et
      inversement taper dans le texte libre deselectionne la combo box,
      via on_value_change() de chaque widget. _build_payload() prend la
      valeur du select si non vide, sinon celle de l'input. Une icone "+"
      (add_circle) a cote de la combo box ouvre une petite boite de
      dialogue (_on_add_free_text_option) pour AJOUTER UNE NOUVELLE
      OPTION EN DIRECT : ajoutee a select_widget.options (utilisable/
      selectionnee immediatement, sans redemarrer) ET a free_text
      ["options"] (le MEME dict que celui charge depuis templates.json,
      voir interface.build_body - donc persistee dans le fichier via
      self._on_config_changed(), fourni par add_button). scene_button.py
      ne sait pas ou/comment ecrire templates.json (separation des
      responsabilites, section 11) : on_config_changed est une simple
      callback fournie par interface.py (persist_templates(), qui
      reecrit raw_configs entier via buttons_config.save_button_configs).
      IMPORTANT : build_body charge templates.json UNE SEULE FOIS via
      load_raw_configs() (pas un load_button_configs()/load_column_titles
      () independants comme avant) precisement pour que les dicts
      free_text passes aux SceneButton soient les MEMES objets que ceux
      contenus dans raw_configs - une mutation de l'un mute l'autre,
      necessaire pour que la persistance reflete bien l'ajout.
PIEGES DEJA RENCONTRES sur cette fonctionnalite (a ne pas refaire) :
    - Un ui.select seul en mode combo box Quasar (props use-input +
      new-value-mode="add-unique") a ete essaye en premier pour a la fois
      choisir dans une liste ET taper une valeur hors liste dans le meme
      widget : ne fonctionne pas de facon fiable (le wrapper NiceGUI/
      QSelect tend a re-contraindre la valeur aux options connues).
    - Un ui.input + <datalist> HTML natif a ensuite ete essaye (texte
      libre garanti + suggestions cliquables) : fonctionnellement
      correct, mais rejete par l'utilisateur au profit du design a deux
      lignes separees ci-dessus (comportement explicitement demande).
La valeur courante de chaque champ est incluse dans le payload a chaque
play/update_data (pas de capture "une seule fois" comme bib_on/target_on).
Les champs sont desactives (widget.disable()) des que l'etat n'est plus
idle, et reactives au retour a idle (stop, reset_to_idle) - evite de
changer une valeur pendant que le graphique est deja affiche.

Bouton "intermediaire" (intermediate_on=True, intermediate_type="shoot_out"
/ "slope" / "relay", field_intermediate="timekey" par defaut) : combo box
(ui.select) affichee SOUS le bouton, listant les intermediaires
ACTUELLEMENT en course pour ce type, calcules par
_current_intermediate_options() a partir de data.config.interorder (voir
biathdata_reference.txt section 1 : liste ordonnee des noms de cles
reellement utilises par CETTE course - contient aussi C_RELAY1/2/3 si et
seulement si le format de course actuel en est un) filtree par prefixe
("shoot_out" -> "C_INTERSHOOT", "slope" -> "C_INTERSLOPE", "relay" ->
"C_RELAY" ; attention "C_INTERSHOOT".startswith exclut bien
C_INTERINSHOOT*, prefixe different malgre la ressemblance). CORRECTION
D'UNE ERREUR PRECEDENTE : "relay" a d'abord ete implemente avec une liste
FIXE C_RELAY1..3 codee en dur (en supposant, a tort, que interorder ne
contenait jamais de cles C_RELAY) - corrige suite a une remarque directe
de l'utilisateur : interorder PEUT contenir C_RELAY1/2/3 si le format de
course en est un, donc "relay" utilise le meme filtrage dynamique que les
deux autres types, pas de cas particulier dans le code.
_refresh_intermediate_options(), sur un ui.timer(1.0, ...) propre a chaque
bouton intermediate_on, resynchronise la liste d'options en direct (utile
car le websocket se connecte APRES la construction de l'interface -
data.config peut valoir None au demarrage) et reinitialise la selection
si elle n'est plus valide. La valeur choisie est poussee immediatement via
update_template si le graphique est deja affiche (pas de capture "au
premier play" ici, contrairement a bib_on/target_on - changer
d'intermediaire en direct est le but recherche). Tant qu'aucun
intermediaire n'est choisi, _build_payload bloque le play/l'update (renvoie
None, notifie l'operateur) - verifie EN PREMIER, avant meme de demander le
dossard (bib_on), pour ne pas faire perdre ce travail a l'operateur si
l'intermediaire s'avere manquant ensuite.

Restriction par format de course (race_formats=["PURSUIT", ...], optionnel,
None par defaut) : _is_format_available() compare data.event_infos
.RACEFORMAT (voir biathdata_reference.txt section 2, ex: "MASSSTART") a
cette liste. Si le format actuel n'y figure pas, TOUT le bouton devient
inutilisable - _refresh_appearance() le grise entierement (bg-slate-300,
cursor-not-allowed, label en slate-500, survol IN/OUT force invisible/
pointer-events-none) ET _on_main_click/_on_hover_click/_on_next_page/
_on_prev_page retournent immediatement sans effet (double protection :
visuelle + logique). Une icone "block" grise apparait a cote du bouton
(meme emplacement que l'icone de connexion) avec un tooltip expliquant le
format actuellement detecte. _refresh_format_availability(), sur un
ui.timer(1.0, ...) propre a chaque bouton race_formats, revalidate chaque
seconde (le format peut n'etre connu qu'apres coup, meme raison que pour
intermediate_on). Omettre race_formats (None) = bouton actif pour tous les
formats, comportement inchange par rapport a avant cette fonctionnalite.

Un seul occupant a la fois par slot CasparCG partage entre boutons :
    - Preview : un seul layer de preview pour tous les boutons. Mettre un
      bouton en preview clear() de force la preview (immediat, sans
      animation) et remet a idle (reset_to_idle()) le bouton qui
      l'occupait avant (SceneButton._active_preview).
    - Programme : un (layer, cg_layer) donne ne peut avoir qu'un seul
      occupant (SceneButton._active_pgm, dict indexe par (layer,
      cg_layer)). Si un bouton est envoye au programme (play direct ou
      Take) sur le meme (layer, cg_layer) qu'un bouton deja a l'antenne,
      ce dernier est stoppe (stop(), meme mecanisme que le bouton "OUT"
      manuel, avec l'auto-remove differe habituel) avant le chargement du
      nouveau.
    - SceneButton.reset_all() (utilise par l'Emergency All Out, voir
      build_header) remet TOUS les boutons a idle et vide ces deux
      registres.
    - SceneButton.stop_all_pgm() (async, utilise par le bouton ALL OUT du
      footer, voir build_footer) stoppe tous les boutons actuellement au
      programme (appelle button._stop() sur chacun, meme mecanisme que le
      survol "OUT"), sans toucher a la preview.
    - SceneButton.reset_preview_button() (utilise par le bouton CLEAR PRW
      du footer) remet a idle le bouton qui occupe SceneButton
      ._active_preview, sans envoyer de commande AMCP - a appeler APRES
      un clear direct de caspar.clear("prw", ...) fait par l'appelant
      (meme repartition des roles que caspar.emergency_all_out() +
      SceneButton.reset_all() dans on_emergency_click).

Indicateur de connexion : une icone "warning" rouge apparait a droite du
bouton (propre a chaque instance de SceneButton, verifiee chaque seconde
via son propre ui.timer) si caspar.connected est False et/ou si
data.connected est False. Un tooltip rouge (bg-red-600) affiche au
survol le detail du/des probleme(s) ("CasparCG deconnecte" et/ou
"WebSocket deconnecte").

Couleur du corps du bouton selon l'etat : idle = gris (slate-700),
preview = jaune (yellow-600), programme = rouge (red-600).

ASSOMPTIONS A CONFIRMER (choix faits faute de precision, a valider a
l'usage) :
    - 3e clic sur le corps du bouton une fois au programme : aucun effet.
    - target_on ne se redeclenche pas lors du Take, seulement au premier
      play.
    - bib_on ne se redeclenche pas non plus lors du Take.


8. LECONS / PIEGES NICEGUI DECOUVERTS PENDANT LE DEVELOPPEMENT
------------------------------------------------------------------

Ces points ont coute du temps de debogage et doivent etre gardes en tete
pour la suite du developpement de l'interface :

8.1 .classes(replace=...) remplace TOUTES les classes, y compris celles
    posees par defaut par NiceGUI/Quasar (ex: la classe "flex" implicite
    d'un ui.row()). Oublier de la reinclure casse silencieusement le
    layout (ex: une icone qui ne reste plus sur la meme ligne qu'un
    texte). Toujours reinclure explicitement "flex" (et tout autre
    classe de base necessaire) dans la string de remplacement.

8.2 ui.button(..., color=None) est necessaire pour desactiver la couleur
    "primary" (bleue) que Quasar applique par defaut aux boutons ; sinon
    les classes Tailwind de couleur (text-*, bg-*, border-*) sont
    silencieusement ignorees/ecrasees.

8.3 ui.image(source) : passer un pathlib.Path (pas une simple string) est
    necessaire pour que NiceGUI reconnaisse un fichier local et le serve
    automatiquement via une route interne. Une string est envoyee telle
    quelle comme attribut src au navigateur (resolue relativement a
    l'URL de la page, pas au filesystem serveur -> 404 silencieux). Voir
    aussi : dimensionner avec des tailles fixes (h-10 w-16) plutot que
    w-auto, qui peut mal se comporter avec le composant Quasar QImg
    sous-jacent.

8.4 Pour un focus fiable dans une ui.dialog(), combiner
    .props("autofocus") ET un ui.timer(0.1, lambda: el.run_method
    ("focus"), once=True) de secours (l'autofocus HTML seul est parfois
    rate a cause de l'animation d'ouverture de Quasar).

8.5 PIEGE MAJEUR - "auto-index page" : si du code NiceGUI est ecrit au
    niveau module (en dehors d'une fonction decoree @ui.page), NiceGUI le
    re-execute INTEGRALEMENT (y compris de simples assignations Python
    comme la creation d'instances CasparCG/BiathDataWebsocket) a CHAQUE
    nouvelle connexion/reconnexion de client navigateur. Consequence
    reelle rencontree : des instances caspar/data toutes neuves (jamais
    connectees) etaient recreees a chaque chargement de page, rendant
    orphelines celles connectees dans @app.on_startup - l'interface
    affichait donc "deconnecte" en permanence alors que la connexion
    reelle fonctionnait tres bien en arriere-plan. SOLUTION APPLIQUEE :
    creer les instances caspar/data au vrai niveau module (une seule
    fois, avant tout ui.run()), et envelopper toute la construction de
    l'UI dans une fonction @ui.page("/") qui, elle, peut etre re-executee
    par client sans consequence puisqu'elle ne fait que REFERENCER les
    objets globaux existants. Diagnostic : comparer id(caspar)/id(data)
    entre le point de connexion et le point d'affichage a permis de
    confirmer le probleme.

8.6 reload=False dans ui.run() est garde par prudence/bonne pratique pour
    une appli avec des connexions/taches de fond persistantes (evite les
    complications potentielles du sous-processus de rechargement de
    uvicorn/NiceGUI), meme si ce n'etait PAS la cause reelle du bug 8.5.

8.7 ui.dialog() utilise en `valeur = await dialog` ouvre automatiquement
    la boite de dialogue et suspend jusqu'a dialog.submit(valeur) - motif
    pratique pour des flux de saisie modale (utilise pour bib_on et
    target_on).

8.8 PIEGE - une grille "ligne/colonne" faite de plusieurs ui.row()
    flex-wrap independantes (une par ligne) NE PRODUIT PAS un alignement
    de colonnes entre les lignes. Chaque ui.row() flex est son propre
    contexte : "colonne N" n'y designe que le N-ieme enfant de CETTE ligne
    precise, base sur son propre contenu, sans lien avec les autres
    lignes. Consequence reelle rencontree (interface.build_body) : un
    bouton place en (row=2, column=5) apparaissait juste apres celui en
    (row=2, column=1) au lieu de s'aligner sous la colonne 5 de la ligne 1,
    car la ligne 2 n'avait que 2 boutons (donc 2 "cases" flex, pas 5).
    SOLUTION APPLIQUEE : conteneur de section en display:grid (Tailwind
    "grid"), chaque case etant un ui.column positionne explicitement via
    le style CSS `grid-row: N; grid-column: M;`. Une vraie grille CSS
    partage ses pistes de colonnes entre toutes les lignes, donc la
    colonne M s'aligne verticalement partout, quel que soit le nombre
    d'entrees des autres lignes.

8.9 PIEGE - ui.header()/ui.footer() (QHeader/QFooter Quasar) sont
    positionnes plein-largeur par rapport au VIEWPORT par defaut,
    independamment du padding applique au conteneur de contenu de page
    (.nicegui-content, qui a un padding par defaut non nul). Consequence
    reelle rencontree : le header, indente uniquement via son propre m-3,
    et le corps de page (build_body), indente via son propre px-3 MAIS
    A L'INTERIEUR du padding par defaut de .nicegui-content, ne
    s'alignaient pas horizontalement - le corps apparaissait plus
    indente que le header.
    SOLUTION APPLIQUEE (build_header) :
    ui.query(".nicegui-content").style("padding-left: 0; padding-right: 0;")
    pour ramener le corps de page au meme repere horizontal (le viewport)
    que le header/footer, puis chaque conteneur (header m-3, corps px-3,
    footer m-3) reproduit lui meme le meme inset de 12px pour rester
    visuellement aligne. Utiliser .style() et non .classes(replace=...)
    ici, pour ne pas casser d'eventuelles classes flex/gap internes de
    NiceGUI sur cet element (meme categorie de piege que 8.1).
    PIEGE DANS LE PIEGE (regression reelle rencontree et corrigee) : la
    toute premiere version de ce correctif utilisait
    ui.query(".nicegui-content").style("padding: 0;") (les 4 cotes, pas
    seulement gauche/droite). Or Quasar calcule DYNAMIQUEMENT un
    padding-top sur ce meme element .nicegui-content pour pousser le
    contenu sous le QHeader (positionne en "fixed", donc superpose au
    contenu par defaut sans ce decalage). Mettre "padding: 0" ecrasait
    aussi ce padding-top -> le corps de page (build_body) se retrouvait
    affiche SOUS/DERRIERE le header au lieu d'etre entre le header et le
    footer. D'ou la version finale ci-dessus, qui ne touche QUE
    padding-left/padding-right et laisse Quasar gerer padding-top/bottom.

8.10 TECHNIQUE - reduire toute une zone de l'UI (boutons, texte, grilles...)
    sans retoucher chaque classe Tailwind individuellement : propriete CSS
    "zoom" (pas transform:scale, qui ne modifie pas la taille de boite
    dans le flux et provoquerait un chevauchement avec les elements
    suivants). Utilise dans interface.build_body via BODY_ZOOM (0.8 par
    defaut, seule valeur a modifier pour retoucher la taille globale) sur
    le conteneur du corps de page uniquement (header/footer non concernes,
    en dehors de ce conteneur). PIEGE associe : zoom retrecit aussi la
    boite de l'element dans le flux normal (contrairement a
    transform:scale) - une hauteur fixe (ex: h-[calc(100vh-190px)]) doit
    donc etre compensee (divisee par BODY_ZOOM) AVANT le zoom pour que la
    hauteur RENDUE, une fois le zoom applique, reste correcte (sinon un
    vide apparait avant le footer). "zoom" est un standard CSS relativement
    recent avec un support navigateur bon mais pas universel (Firefox
    seulement depuis mi-2024) - a garder en tete si l'appli doit un jour
    tourner sur un navigateur different de Chrome/Edge.

10. DECISIONS ENCORE A PRENDRE
-------------------------------

Resolues depuis la version precedente de ce fichier :
    - Format des messages WebSocket : CONNU (voir section 5.4 et
      biathdata_reference.txt), meme si "d'autres types de messages"
      restent a documenter/gerer.
    - Mecanisme du Take preview -> programme : CHOISI (recopie de la
      commande et des donnees via play_prw_to_pgm, pas de clonage de
      composition ni de continuite d'animation).
    - Necessite d'un proxy WebSocket : NON, les templates HTML se
      connectent directement au serveur de donnees (confirme par le
      mecanisme send_ip qui transmet l'IP du websocket au template).
    - Format XML des donnees de template : CONFIRME (templateData/
      componentData, noms de champs = vrais noms metier du template).
    - Persistance de configuration des boutons : CHOISI (fichier
      templates.json, lu par buttons_config.load_button_configs() et
      consomme par interface.build_body ; voir section 2). Ajouter un
      graphique ne necessite plus de modifier le code Python.

Toujours ouvertes :
    - Adresse/port DEFINITIFS (production) de CasparCG et du serveur de
      donnees WebSocket.
    - Version definitive de CasparCG a cibler (2.3.1-lts-stable teste).
    - Liste des templates de la V1 et leurs parametres exacts (seul un
      template placeholder "test" existe actuellement).
    - Organisation des fichiers HTML CasparCG, conventions de nommage.
    - Execution sur un seul PC ou plusieurs machines du reseau ; nombre
      d'operateurs simultanes (l'architecture actuelle suppose UNE seule
      paire caspar/data partagee globalement, pas une instance par
      operateur).
    - Authentification et gestion des droits : non implementees.
    - Journal des actions : non implemente (choix explicite de
      l'utilisateur : les logs cote CasparCG suffisent pour l'instant).
    - Restauration apres redemarrage : self._preview et les taches
      d'auto-remove sont perdues si le process redemarre (etat en
      memoire uniquement, juge acceptable pour l'instant).
    - Signification exacte de C_START (unite probable : millisecondes
      depuis minuit, non confirmee), VOLADBNUMBER, C_SHOOTING_RACE_NUMBER.
    - Gestion des "autres types de messages" WebSocket (ignores pour
      l'instant, cote biathdata_ws.py).
    - Catalogue reel des templates CasparCG et de leurs champs : le
      mecanisme pour les ajouter existe desormais (templates.json, voir
      section 2), mais le contenu reste a completer par l'utilisateur
      au-dela du placeholder STARTLIST.
    - Adaptation des boutons au format de course (nombre de tours/tirs,
      variantes d'epreuve) pour ne pas afficher, par exemple, des
      intermediaires qui n'existent pas sur ce format : evoque par
      l'utilisateur comme prochaine etape, pas encore implemente (voir
      section 12).


11. REGLES POUR LES FUTURES IA
-------------------------------

Avant de modifier le code, une IA doit :

- Lire ce fichier en entier.
- Lire biathdata_reference.txt avant de toucher au parsing des donnees
  de chronometrage.
- Distinguer les exigences confirmees (sections 4 a 9) des points encore
  ouverts (section 10).
- Conserver la separation des responsabilites : casparcg.py et
  biathdata_ws.py ne contiennent AUCUNE logique d'affichage ; interface.py
  et scene_button.py ne contiennent AUCUNE logique bas niveau AMCP/
  WebSocket (ils appellent uniquement les methodes publiques documentees

13. COMPILATION EN EXECUTABLE (PyInstaller / auto-py-to-exe)
------------------------------------------------------------------

Objectif : pouvoir installer le logiciel sur un PC (hors environnement de
developpement Python) tout en continuant a l'utiliser normalement en mode
developpement (python main.py depuis le repo) - les deux doivent marcher
sans changement manuel entre les deux.

13.1 paths.py - fondation necessaire a la compilation
    Deux categories de fichiers, deux fonctions (voir aussi section 2) :
    - resource_path() : ressources EN LECTURE SEULE embarquees dans
      l'executable (assets/foxxprod_logo.png, templates.json "de base").
      En mode installe (FROZEN=True, attribut sys.frozen ajoute par le
      bootloader PyInstaller), pointe vers sys._MEIPASS - un dossier
      d'extraction TEMPORAIRE, different a chaque lancement, jamais a
      utiliser pour un fichier qu'on veut ecrire ou retrouver au
      prochain demarrage.
    - user_data_path() : fichiers UTILISATEUR modifiables par le
      logiciel lui-meme (config.json, templates.json une fois copie). En
      mode installe, %APPDATA%\BiathControlCenter (zone ecrivable SANS
      droits administrateur, contrairement au dossier d'installation
      habituel sous Program Files - point important, CasparCG tourne
      souvent sur un PC de regie sans compte admin permanent). En
      developpement, la racine du projet (FROZEN=False -> comportement
      strictement identique a avant l'introduction de paths.py).
    - ensure_user_file(filename) : au tout premier lancement en mode
      installe, si le fichier utilisateur n'existe pas encore, le copie
      depuis la ressource embarquee du meme nom (templates.json "de
      base" livre avec le logiciel) - sans jamais ecraser une copie
      utilisateur deja modifiee. Utilise pour templates.json (contenu
      significatif a preserver), PAS pour config.json (dont l'absence
      est deja geree nativement par app_config.load_config() via
      DEFAULT_CONFIG, pas besoin de "graine").

    interface.py (LOGO_PATH), buttons_config.py (BUTTONS_CONFIG_PATH) et
    app_config.py (CONFIG_PATH) passent tous les trois par paths.py -
    aucun ne construit plus son propre chemin via Path(__file__)
    directement (verifie : seul paths.py y fait encore reference).

13.2 BiathControlCenter.spec - configuration PyInstaller
    A compiler avec `pyinstaller BiathControlCenter.spec` (plus fiable et
    reproductible que de reconfigurer manuellement l'interface graphique
    auto-py-to-exe a chaque fois - auto-py-to-exe N'EST QU'UNE interface
    graphique par-dessus PyInstaller, elle ne charge pas directement un
    fichier .spec existant). Points cles :
    - Mode "onedir" (COLLECT, pas juste EXE onefile) : demarrage plus
      rapide qu'un onefile qui doit se re-extraire dans un dossier
      temporaire a CHAQUE lancement - preferable pour un usage en direct
      pendant une diffusion, ou la reactivite au demarrage compte.
    - collect_all("nicegui") (PyInstaller.utils.hooks) : NiceGUI embarque
      ses propres ressources statiques (JS/CSS/polices/favicon) qui
      doivent etre incluses telles quelles, sinon l'interface ne se
      charge pas une fois compile - piege documente par NiceGUI elle-meme
      pour tout packaging PyInstaller/Nuitka, pas verifie en pratique ici
      (pas d'environnement de build disponible pour tester la compilation
      elle-meme) mais applique par prudence.
    - datas inclut assets/ (logo) et templates.json (catalogue "de base",
      voir 13.1) - PAS config.json (jamais embarque, uniquement cree/lu
      dans %APPDATA% en mode installe).
    - console=True (choix delibere, PAS le defaut "propre" console=False
      d'une appli Windows) : main.py affiche l'etat de connexion CasparCG/
      WebSocket via print() au demarrage, et des erreurs peuvent remonter
      sur stdout/stderr en cours d'usage (ex: le ConnectionResetError
      deja rencontre en developpement, section historique du projet).
      PIEGE PyInstaller CONNU : en mode "windowed" (console=False),
      sys.stdout/stderr valent None dans un executable sans console - un
      print() ou un traceback non catche peut alors LEVER UNE EXCEPTION
      au lieu de simplement s'afficher, ce qui est pire qu'une fenetre de
      console en plus. A ne repasser en console=False que si le logiciel
      est juge stable ET qu'aucun print()/traceback resultant n'est plus
      possible.
    - main.py utilise deja reload=False dans ui.run() (piege 8.6,
      necessaire pour un executable compile - NiceGUI reload=True repose
      sur un mecanisme de re-spawn de process qui ne marche pas une fois
      frozen). Deja correct avant ce travail de compilation, rien a
      changer ici.

13.3 requirements.txt
    Dependances RUNTIME seulement (nicegui, websockets), epinglees aux
    versions utilisees en developpement (nicegui 3.16.0, websockets
    15.0.1 au moment ou ce travail a ete fait). PyInstaller et
    auto-py-to-exe sont des OUTILS DE BUILD (deja installes separement
    dans l'environnement de developpement au moment de ce travail :
    PyInstaller 6.11.1, auto-py-to-exe 2.45.0), pas des dependances de
    l'application elle-meme - volontairement absents de requirements.txt.

13.4 Non verifie / a tester
    Aucune compilation reelle n'a ete effectuee pendant ce travail (pas
    d'environnement de build/execution disponible pour lancer
    `pyinstaller BiathControlCenter.spec` et verifier l'executable
    resultant). A tester avant un usage en production :
    - Que l'executable demarre bien et que l'UI NiceGUI se charge
      (risque principal : ressources NiceGUI manquantes malgre
      collect_all, cas documente comme frequent pour ce framework).
    - Que templates.json est bien copie dans %APPDATA%\BiathControlCenter
      au premier lancement, et que les ecritures ulterieures (ajout
      d'option de free_text, futures fonctionnalites) persistent bien
      la-bas et pas dans le dossier d'installation.
    - Que config.json se cree correctement au premier lancement dans le
      meme dossier %APPDATA%.
    - Icone : icon.ico (racine du projet, PAS encore ajoute au repo au
      moment ou ceci est ecrit) utilise a DEUX endroits distincts, a ne
      pas confondre : icon="icon.ico" dans EXE() (icone du fichier .exe,
      gravee a la compilation) ET dans `datas` + main.py
      (resource_path("icon.ico"), passe a ui.run(favicon=...) - copie
      embarquee lue A L'EXECUTION pour l'onglet du navigateur, PyInstaller
      ne rend pas l'icone .exe elle-meme accessible comme fichier une
      fois compilee). favicon= est optionnel cote code (retombe sur None
      si icon.ico est absent, ne bloque pas le demarrage), mais icon.ico
      DOIT exister pour que la compilation reussisse (les deux endroits
      y font reference sans verification d'existence a la compilation).
      PIEGE COURANT (pas un bug de compilation) : l'icone du .exe
      n'apparaissant pas dans l'Explorateur Windows apres compilation est
      generalement le CACHE D'ICONES Windows, pas un probleme reel - voir
      compiler.txt pour les solutions (renommer le fichier, redemarrer
      l'Explorateur, etc.).
