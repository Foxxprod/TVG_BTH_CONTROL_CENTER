BIATH CONTROL CENTER - CONTEXTE DU PROJET
============================================

Ce fichier a ete entierement reecrit le 25/08/2026 pour refleter l'etat reel
du projet apres une premiere phase de developpement. Il remplace la version
initiale (qui decrivait un projet vide, au stade de conception).


1. OBJECTIF DU PROJET
----------------------

Biath Control Center est un logiciel de controle pour piloter les habillages
televisuels pendant une course de biathlon.

Le logiciel permet a un operateur de suivre les donnees de la course en
temps reel et de declencher les habillages graphiques dans CasparCG de
maniere rapide, fiable et comprehensible pendant une diffusion en direct.

Un logiciel distinct (deja existant, non modifie par ce projet) genere et
diffuse les donnees de la course de biathlon via WebSocket. Biath Control
Center consomme ces donnees et pilote CasparCG ; il ne remplace pas le
logiciel de donnees.


2. ETAT ACTUEL DU REPO
----------------------

Fichiers principaux :

- main.py
    Point d'entree. Cree les instances globales `caspar` (CasparCG) et
    `data` (BiathDataWebsocket), declare la page NiceGUI ("/"), appelle
    build_header() et build_body(), connecte caspar/data au demarrage du
    serveur (@app.on_startup), lance ui.run().

- casparcg.py
    Couche de communication AMCP avec CasparCG. Implementation maison
    (pas de librairie tierce) : ouverture de socket TCP brut, envoi de
    commandes texte, parsing des reponses selon le protocole AMCP.
    Contient la classe CasparCG et le dataclass AMCPResponse.

- biathdata_ws.py
    Couche de communication WebSocket avec le logiciel de donnees
    biathlon. Utilise la librairie tierce `websockets` (contrairement a
    casparcg.py, le protocole WebSocket est trop complexe/risque a
    reimplementer a la main). Contient la classe BiathDataWebsocket.

- interface.py
    Construction de l'interface NiceGUI : barre d'outils du haut
    (build_header) et corps de page (build_body). Ne contient aucune
    logique bas niveau AMCP/WebSocket, uniquement de l'affichage et des
    appels aux methodes publiques de CasparCG/BiathDataWebsocket.

- scene_button.py
    Classe SceneButton : brique reutilisable representant un graphique
    CasparCG pilotable (play preview/programme, take, stop, pages
    multiples, saisie de dossard, saisie de valeur target, envoi
    automatique de l'ip du websocket). C'est le mecanisme prevu pour
    ajouter facilement de nouveaux graphiques a l'interface.

- biathdata_reference.txt
    Documentation de reference de tous les champs disponibles dans un
    message de chronometrage recu via le WebSocket (config, event_infos,
    timing_data), avec leur variable d'acces Python exacte. Genere a
    partir d'un exemple reel fourni par l'utilisateur.

- assets/foxxprod_logo.png
    Logo affiche dans la barre d'outils.

- biath_data.py
    Fichier historique vide, non utilise. La logique WebSocket vit en
    realite dans biathdata_ws.py (renomme/reoriente en cours de route).
    A supprimer ou fusionner si confirme inutile.

Version de Python utilisee en developpement : 3.13 (Python313, observe
dans les chemins d'execution). Version de CasparCG testee : 2.3.1-lts-stable.


3. TECHNOLOGIES CONFIRMEES
---------------------------

- Python (3.13 en dev).
- NiceGUI pour l'interface operateur (confirme et utilise).
- asyncio pour tout le code reseau et les taches de fond (reconnexion,
  ping, retrait automatique de graphiques...).
- Client AMCP : implementation interne maison sur socket TCP brut (pas de
  librairie tierce). Choix assume : protocole texte simple, controle total
  du comportement (timeouts, reconnexion), pas de dependance externe a
  maintenir pour un usage broadcast en direct.
- Client WebSocket : librairie tierce `websockets` (pip install websockets).
  Choix assume different d'AMCP : le protocole WebSocket (handshake HTTP
  Upgrade, framing, masking, ping/pong de controle) est trop complexe et
  risque a reimplementer correctement a la main.
- Aucune API web publique construite par-dessus NiceGUI : NiceGUI gere la
  communication navigateur <-> serveur en interne.


4. CASPARCG.PY - DETAIL DE L'IMPLEMENTATION
---------------------------------------------

4.1 AMCPResponse (dataclass)
    - code: int, message: str, data: list[str]
    - is_info      -> 100 <= code < 200
    - is_success    -> 200 <= code < 400
    - is_error      -> code == 0 (erreur locale/reseau) ou code >= 400

4.2 Classe CasparCG - constructeur
    CasparCG(ip, port, channel_programm, channel_preview, timeout=5.0,
             reconnect=True, reconnect_delay=5.0)
    channel_programm/channel_preview DOIVENT correspondre aux channels
    reellement definis dans le casparcg.config du serveur CasparCG cible
    (voir section 7, un mismatch a deja cause une erreur "Invalid channel
    specified").

    Etat interne : reader/writer asyncio, connected (bool), _lock
    (asyncio.Lock, serialise les commandes), _preview (dict, dernier
    template/data/cg_layer/play_on_load envoye en preview), _ping_interval
    (5.0s), _ping_task, _remove_delay (5.0s), _pending_removals (dict
    (address, cg_layer) -> Task, pour l'auto-remove differe apres stop()).

4.3 Fonctions internes/techniques (prefixees _, ou non destinees a un
    usage direct depuis le reste du logiciel) :
    - ping() : envoie "PING\r\n", compare la reponse brute a "PONG" (PING
      est un cas special du protocole AMCP, il ne suit PAS le format
      "XXX message" standard), met a jour self.connected.
    - _ping_loop() : boucle unique de fond. Si connecte -> attend
      ping_interval puis ping(). Si deconnecte et self.reconnect ->
      attend reconnect_delay puis _reconnect(). Sinon, arrete la boucle.
      Sequentiel : jamais deux tentatives de reconnexion en parallele.
    - _reconnect() : ferme l'ancienne connexion si presente, en ouvre une
      nouvelle, appelle ping().
    - send_command(command) : envoie une commande AMCP brute, retourne un
      AMCPResponse. Retourne code=0 "Not connected" si non connecte.
    - _read_response() : parse une reponse (code + message), et pour les
      reponses multi-lignes (code 200), continue de lire jusqu'a une
      ligne vide terminale.
    - _channel_number(channel) : "prw" -> channel_preview, "pgm" ->
      channel_programm, sinon ValueError.
    - format_address(channel, layer=None) : "prw" -> toujours
      "{channel_preview}-1" (layer ignore, force a 1). "pgm" -> exige un
      layer explicite (ValueError sinon).
    - _escape_amcp_string(value) / _escape_xml(value) : echappement pour
      parametres AMCP entre guillemets et pour attributs XML.
    - format_template_data(data: dict) : convertit un dict cle/valeur en
      XML CasparCG classique :
        <templateData><componentData id="CLE"><data id="text"
        value="VALEUR"/></componentData>...</templateData>
      CONFIRME avec un exemple XML reel fourni par l'utilisateur. Les
      cles du dict correspondent aux VRAIS noms de champs du template
      (pas de convention generique f0/f1) : chaque template a ses propres
      noms de champs.
    - _schedule_remove(...) / _delayed_remove(...) : programment un
      CG REMOVE automatique remove_delay secondes apres un stop(), annule
      si un nouveau graphique est charge sur le meme (channel-layer,
      cg_layer) avant l'echeance.

4.4 Fonctions publiques (a utiliser depuis le reste du logiciel) :
    - connect() : ouvre la connexion TCP, verifie via PING/PONG, DEMARRE
      TOUJOURS la boucle de fond _ping_loop meme si cette premiere
      tentative echoue (pour que CasparCG indisponible au demarrage soit
      retente automatiquement au lieu d'abandonner). Retourne None ou un
      message d'erreur.
    - disconnect() : envoie BYE (sur, car on est toujours en connexion
      distante/reseau, jamais en console locale CasparCG - BYE ne fait
      donc que deconnecter, il n'eteint pas le serveur) puis ferme le
      socket. Annule _ping_task et toutes les taches _pending_removals.
    - play_template(channel, template, data=None, layer=None, cg_layer=1,
      play_on_load=True) : construit et envoie CG ADD. Si succes, annule
      tout auto-remove programme pour ce (channel-layer, cg_layer), et si
      channel=="prw", memorise l'etat dans self._preview.
    - update_template(channel, data, layer=None, cg_layer=1) : CG UPDATE.
      Met a jour self._preview["data"] si c'est la preview qui est mise a
      jour avec succes.
    - remove_template(channel, layer=None, cg_layer=1) : CG REMOVE
      (retire completement le producer, contrairement a stop()).
    - stop(channel, layer=None, cg_layer=1) : CG STOP, puis programme un
      CG REMOVE automatique 5s plus tard (annulable, voir 4.3).
    - clear(channel, layer=None) : CLEAR generique (retire N'IMPORTE quel
      producer, video/image/graphique, pas seulement les templates CG).
      Si layer est omis, clear tout le channel. Reinitialise self._preview
      si c'est la preview qui est cleared avec succes.
    - play_prw_to_pgm(layer) : le "Take". Rejoue (recopie la commande et
      les donnees, choix assume plutot que cloner une composition deja
      preparee) le template/data actuellement memorise en preview vers le
      programme au layer donne, puis stoppe la preview. Retourne une
      erreur "Nothing in preview to take" si rien n'a ete joue en preview
      au prealable (ou si le dernier play a echoue).
    - emergency_all_out() : clear("prw") + clear("pgm"), retourne les deux
      AMCPResponse. Vide integralement les deux channels (tout producer,
      y compris les graphiques).

4.5 Rappels de protocole AMCP (source : wiki AMCP CasparCG, la doc note
    elle-meme qu'elle peut etre datee, a re-verifier avec
    casparcg.com/docs/wiki si besoin) :
    - Reponses : code 3 chiffres + message. 100-101 info. 200-202 succes
      (200 = multi-lignes terminees par une ligne vide, 201/202 = une
      seule ligne). 400-404 erreur client. 500-503 erreur serveur.
    - Encodage UTF-8, terminaison de commande "\r\n".
    - Parametres avec espaces entre guillemets, echappement \" et \\.
    - Adressage channel-layer : "1" (tout le channel), "1-1", "1-10",
      "-0" (layer par defaut).
    - CG ADD [layer] "template" [play-on-load 0/1] {"data"}
    - CG UPDATE [cg_layer] "data"
    - CG REMOVE [cg_layer]
    - CG STOP [cg_layer]
    - CG CLEAR (sans cg_layer, ne retire que les templates CG)
    - CLEAR (generique, retire tout producer)
    - BYE deconnecte a distance / eteint le serveur en local.


5. BIATHDATA_WS.PY - DETAIL DE L'IMPLEMENTATION
--------------------------------------------------

5.1 Classe BiathDataWebsocket - constructeur
    BiathDataWebsocket(ip, port, path="/", timeout=5.0, reconnect=True,
                        reconnect_delay=5.0)
    url (property) = f"ws://{ip}:{port}{path}"

    Etat expose : latest_data (dict JSON brut du dernier message de
    chronometrage complet), config (SimpleNamespace), event_infos
    (SimpleNamespace), timing_data (dict[str, SimpleNamespace] cle =
    dossard), connected (bool).

5.2 Fonctions publiques :
    - connect() : ouvre la connexion websocket, DEMARRE TOUJOURS la
      boucle de fond _receive_loop meme si la premiere tentative echoue
      (meme logique que CasparCG.connect(), pour retenter automatiquement
      un serveur de donnees indisponible au demarrage).
    - disconnect() : annule _receive_task, ferme la connexion.
    - change_ip(ip, port=None) : met a jour l'adresse ; si deja connecte,
      se deconnecte puis se reconnecte a la nouvelle adresse.

5.3 Fonctions internes :
    - _receive_loop() : boucle unique de fond, meme principe que
      _ping_loop de CasparCG. Si connecte, consomme les messages
      (async for) jusqu'a perte de connexion. Si deconnecte et
      self.reconnect, attend reconnect_delay puis _reconnect(). Jamais
      deux tentatives en parallele.
    - _reconnect() : ferme l'ancien websocket si present, en ouvre un
      nouveau.
    - _handle_message(raw_message) :
        1. json.loads(raw_message). PARTICULARITE DECOUVERTE EN TEST : le
           serveur encode parfois le JSON DEUX FOIS (le message recu est
           une string JSON qui contient elle-meme du JSON en texte
           echappe). Le code detecte ce cas (resultat = str) et refait un
           second json.loads.
        2. Si le dict resultant contient les cles "config", "event_infos"
           ET "timing_data", c'est un snapshot COMPLET de chronometrage
           (pas un delta) : latest_data, config, event_infos et
           timing_data sont remplaces integralement.
        3. D'AUTRES TYPES DE MESSAGES passent sur le meme WebSocket
           (confirme par l'utilisateur) mais ne sont PAS encore geres :
           ils sont ignores silencieusement pour l'instant. A implementer
           plus tard.
    - _sanitize_key(key) : remplace tout caractere non valide pour un
      attribut Python (ex: espace) par "_". Necessaire car le JSON reel
      contient au moins une cle avec espace : "EVENT NAME" ->
      accessible via event_infos.EVENT_NAME.
    - _to_namespace(data: dict) : convertit un dict en SimpleNamespace en
      assainissant les cles.

5.4 Format reel des messages WebSocket : voir biathdata_reference.txt
    pour le detail complet champ par champ. Points cles :
    - Chaque message de chronometrage contient un etat COMPLET (pas un
      delta), a remplacer integralement a chaque reception.
    - timing_data est indexe par dossard (string), ex: "1", "2"...
    - Les noms de champs (C_NUM, C_LAST_NAME, C_TIME, C_STATUS,
      C_INTERSHOOT1..8, C_INTERSLOPE1..12, etc.) sont documentes dans
      biathdata_reference.txt avec leur variable d'acces exacte.
    - C_START et les C_INTER... sont TRES PROBABLEMENT en millisecondes
      depuis minuit (deduit, pas confirme par le fournisseur).
    - VOLADBNUMBER et C_SHOOTING_RACE_NUMBER : signification non
      identifiee avec certitude.

7. SCENE_BUTTON.PY - DETAIL DE L'IMPLEMENTATION
----------------------------------------------------

Classe SceneButton : represente un graphique CasparCG pilotable. Concu
comme LE moyen d'ajouter facilement un nouveau graphique a l'interface et
de controler les donnees qui lui sont envoyees.

Constructeur :
    SceneButton(caspar, data, label, template, layer, cg_layer=1,
                extra_data=None,
                send_ip=False, field_ip="ip",
                bib_on=False, field_bib="bib",
                multipage_on=False, field_page="page",
                target_on=False, field_target="target")

    Les noms de champs (field_ip, field_bib, field_page, field_target)
    sont CONFIGURABLES par bouton (chaque template CasparCG peut avoir
    ses propres noms de champs), SAUF que la VALEUR du champ ip est
    toujours automatiquement celle du serveur websocket (data.ip), non
    saisie par l'operateur. send_ip n'envoie que l'IP, pas le port.

Comportement au clic (corps du bouton, forme pilule rounded-full comme
le bouton EMERGENCY) :
    - etat "idle"      -> clic = play_template vers preview
    - etat "preview"   -> clic = play_prw_to_pgm (Take vers programme)
    - etat "programme" -> clic sans effet (protection contre un replay
      accidentel d'un graphique en direct ; seul le survol "OUT" peut
      l'arreter)

Survol : un petit rectangle apparait directement au-dessus du bouton
(colle, sans espace mort, pour rester cliquable en y deplacant la
souris), fond noir/gris fonce (bg-slate-800) :
    - "IN"  (idle/preview) -> clic = envoi DIRECT au programme (sans
      passer par la preview)
    - "OUT" (programme)    -> clic = stop() du graphique

Multipage (multipage_on=True) : fleches gauche/droite integrees dans le
corps du bouton (chevron_left/chevron_right). Le compteur "page"
s'incremente/decremente SANS limite haute (plancher a 1, decision
utilisateur : "compteur infini"). Si le graphique est deja affiche, le
changement de page pousse immediatement un update_template.

Selection de dossard (bib_on=True) : boite de dialogue avec un champ de
recherche texte (autofocus fiabilise par .props("autofocus") + un
ui.timer de secours qui force le focus), qui filtre en direct la liste
des athletes (data.timing_data, tri par dossard croissant, recherche sur
"dossard - NOM prenom"). Le premier resultat correspondant est surligne
en bleu ; Entree ou le bouton "Valider" le confirme. Chaque ligne de la
liste est aussi cliquable individuellement (selection directe, liste
scrollable). Si le champ de recherche est vide, RIEN n'est surligne/
selectionnable par defaut (il faut taper ou cliquer explicitement). Le
dossard est capture une seule fois au premier play, puis reutilise tel
quel pour le Take (comme les autres donnees memorisees dans
CasparCG._preview).

Saisie de target (target_on=True) : apres le PREMIER play reussi
(preview ou direct-pgm via "IN" ; pas re-demande au moment du Take),
boite de dialogue avec un champ numerique borne entre 1 et 30. La valeur
saisie est envoyee via update_template.

Indicateur de connexion : une icone "warning" rouge apparait a droite du
bouton (propre a chaque instance de SceneButton, verifiee chaque seconde
via son propre ui.timer) si caspar.connected est False et/ou si
data.connected est False. Un tooltip rouge (bg-red-600) affiche au
survol le detail du/des probleme(s) ("CasparCG deconnecte" et/ou
"WebSocket deconnecte").

Couleur du corps du bouton selon l'etat : idle = gris (slate-700),
preview = jaune (yellow-600), programme = rouge (red-600).

ASSOMPTIONS A CONFIRMER (choix faits faute de precision, a valider a
l'usage) :
    - 3e clic sur le corps du bouton une fois au programme : aucun effet.
    - target_on ne se redeclenche pas lors du Take, seulement au premier
      play.
    - bib_on ne se redeclenche pas non plus lors du Take.


8. LECONS / PIEGES NICEGUI DECOUVERTS PENDANT LE DEVELOPPEMENT
------------------------------------------------------------------

Ces points ont coute du temps de debogage et doivent etre gardes en tete
pour la suite du developpement de l'interface :

8.1 .classes(replace=...) remplace TOUTES les classes, y compris celles
    posees par defaut par NiceGUI/Quasar (ex: la classe "flex" implicite
    d'un ui.row()). Oublier de la reinclure casse silencieusement le
    layout (ex: une icone qui ne reste plus sur la meme ligne qu'un
    texte). Toujours reinclure explicitement "flex" (et tout autre
    classe de base necessaire) dans la string de remplacement.

8.2 ui.button(..., color=None) est necessaire pour desactiver la couleur
    "primary" (bleue) que Quasar applique par defaut aux boutons ; sinon
    les classes Tailwind de couleur (text-*, bg-*, border-*) sont
    silencieusement ignorees/ecrasees.

8.3 ui.image(source) : passer un pathlib.Path (pas une simple string) est
    necessaire pour que NiceGUI reconnaisse un fichier local et le serve
    automatiquement via une route interne. Une string est envoyee telle
    quelle comme attribut src au navigateur (resolue relativement a
    l'URL de la page, pas au filesystem serveur -> 404 silencieux). Voir
    aussi : dimensionner avec des tailles fixes (h-10 w-16) plutot que
    w-auto, qui peut mal se comporter avec le composant Quasar QImg
    sous-jacent.

8.4 Pour un focus fiable dans une ui.dialog(), combiner
    .props("autofocus") ET un ui.timer(0.1, lambda: el.run_method
    ("focus"), once=True) de secours (l'autofocus HTML seul est parfois
    rate a cause de l'animation d'ouverture de Quasar).

8.5 PIEGE MAJEUR - "auto-index page" : si du code NiceGUI est ecrit au
    niveau module (en dehors d'une fonction decoree @ui.page), NiceGUI le
    re-execute INTEGRALEMENT (y compris de simples assignations Python
    comme la creation d'instances CasparCG/BiathDataWebsocket) a CHAQUE
    nouvelle connexion/reconnexion de client navigateur. Consequence
    reelle rencontree : des instances caspar/data toutes neuves (jamais
    connectees) etaient recreees a chaque chargement de page, rendant
    orphelines celles connectees dans @app.on_startup - l'interface
    affichait donc "deconnecte" en permanence alors que la connexion
    reelle fonctionnait tres bien en arriere-plan. SOLUTION APPLIQUEE :
    creer les instances caspar/data au vrai niveau module (une seule
    fois, avant tout ui.run()), et envelopper toute la construction de
    l'UI dans une fonction @ui.page("/") qui, elle, peut etre re-executee
    par client sans consequence puisqu'elle ne fait que REFERENCER les
    objets globaux existants. Diagnostic : comparer id(caspar)/id(data)
    entre le point de connexion et le point d'affichage a permis de
    confirmer le probleme.

8.6 reload=False dans ui.run() est garde par prudence/bonne pratique pour
    une appli avec des connexions/taches de fond persistantes (evite les
    complications potentielles du sous-processus de rechargement de
    uvicorn/NiceGUI), meme si ce n'etait PAS la cause reelle du bug 8.5.

8.7 ui.dialog() utilise en `valeur = await dialog` ouvre automatiquement
    la boite de dialogue et suspend jusqu'a dialog.submit(valeur) - motif
    pratique pour des flux de saisie modale (utilise pour bib_on et
    target_on).

10. DECISIONS ENCORE A PRENDRE
-------------------------------

Resolues depuis la version precedente de ce fichier :
    - Format des messages WebSocket : CONNU (voir section 5.4 et
      biathdata_reference.txt), meme si "d'autres types de messages"
      restent a documenter/gerer.
    - Mecanisme du Take preview -> programme : CHOISI (recopie de la
      commande et des donnees via play_prw_to_pgm, pas de clonage de
      composition ni de continuite d'animation).
    - Necessite d'un proxy WebSocket : NON, les templates HTML se
      connectent directement au serveur de donnees (confirme par le
      mecanisme send_ip qui transmet l'IP du websocket au template).
    - Format XML des donnees de template : CONFIRME (templateData/
      componentData, noms de champs = vrais noms metier du template).

Toujours ouvertes :
    - Adresse/port DEFINITIFS (production) de CasparCG et du serveur de
      donnees WebSocket.
    - Version definitive de CasparCG a cibler (2.3.1-lts-stable teste).
    - Liste des templates de la V1 et leurs parametres exacts (seul un

    - Organisation des fichiers HTML CasparCG, conventions de nommage.

    - Authentification et gestion des droits : non implementees.
    - Journal des actions : non implemente (choix explicite de
      l'utilisateur : les logs cote CasparCG suffisent pour l'instant).
    - Persistance de configuration (templates/boutons definis en dur en
      Python actuellement, pas de fichier de config externe).
    - Restauration apres redemarrage : self._preview et les taches

      memoire uniquement, juge acceptable pour l'instant).
    - Signification exacte de C_START (unite probable : millisecondes

    - Gestion des "autres types de messages" WebSocket (ignores pour

    - Catalogue reel des templates CasparCG et de leurs champs (le

11. REGLES POUR LES FUTURES IA
-------------------------------

Avant de modifier le code, une IA doit :

- Lire ce fichier en entier.
- Lire biathdata_reference.txt avant de toucher au parsing des donnees
  de chronometrage.
- Distinguer les exigences confirmees (sections 4 a 9) des points encore
  ouverts (section 10).
- Conserver la separation des responsabilites : casparcg.py et
  biathdata_ws.py ne contiennent AUCUNE logique d'affichage ; interface.py
  et scene_button.py ne contiennent AUCUNE logique bas niveau AMCP/
  WebSocket (ils appellent uniquement les methodes publiques documentees
  en sections 4.4 et 5.2).
- Ne jamais construire de code UI NiceGUI au niveau module en dehors
  d'une fonction @ui.page(...) - voir le piege 8.5, deja rencontre et
  corrige une fois, a ne pas reintroduire.
- Ne pas envoyer BYE dans un contexte qui pourrait etre une connexion
  locale a la console CasparCG (uniquement sur en connexion reseau
  distante, ce qui est toujours le cas ici).
- Ne pas casser le workflow preview -> Take -> programme, ni la logique
  d'auto-remove differe apres stop() (section 4.3/4.4).
- Toute nouvelle commande AMCP doit etre verifiee contre la doc du wiki
  AMCP CasparCG (avec prudence, la doc peut etre datee) plutot que
  supposee.
- Privilegier des changements petits, testables, compatibles avec un
  usage en direct. Confirmer les hypotheses de format de donnees avec
  l'utilisateur avant de batir dessus (comme cela a ete fait pour le XML
  des templates et le format WebSocket).
- Se referer a la section 8 avant de deboguer un probleme d'affichage
  NiceGUI qui "ne se met pas a jour" ou "n'apparait pas" - plusieurs
  causes racines non intuitives y sont documentees.
